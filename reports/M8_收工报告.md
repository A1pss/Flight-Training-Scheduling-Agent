## 3. 关键决策与理由

### 3.1 ★ egress 的三道闸各管一段，缺一不可

| 闸 | 管什么 | 管不到什么 |
|---|---|---|
| **E2/E3 静态扫描** | 代码里写没写 | **管不到运行时真连了哪** |
| **E1 allowlist 判定** | 判得对不对（含 DNS 投毒、一名多址） | 管不到不走 `core/http.py` 的东西 |
| **E4 运行时抓包** | 实际连了哪 | 只能发现，不能阻止 |

E1 里有两条容易被写漏的格子：**外网域名解析到内网 IP 要放行**（证明拦的是地址
不是名字），**一个名字解析出「一内一外」要整体拒绝**（`any` 会放行、`all` 才对，
攻击形态就是挂两条 A 记录赌实现用 `any`）。

**E4 有一个真实的盲区，实测撞到了**：Python 层 patch `socket.connect` 只抓到
`127.0.0.1:6380`（Redis），**PG 一次都没抓到** —— psycopg 走 libpq，连接在 C 层
建立，根本不经过 `socket.socket.connect`。所以 E4 补了第二条判据：直接问内核
（`/proc/self/fd` 的 socket inode × `/proc/net/tcp`）。那条抓到了 `127.0.0.1:5433`。

> **两条探针都有自检**：`test_e4_baseline_run_touches_the_network_at_all` 与
> `test_e4_kernel_probe_can_actually_see_a_connection`。没有它们，「空列表里没有
> 违规」会绿得非常好看 —— 而那是一个什么都没测的测试。

### 3.2 ★ 两条部署路径比的是黄金用例指纹，不是基准周（`Z-26`）

v6 §11.4 原文说的是「跑同一份黄金用例必须给出逐字节相同的 `content_sha256`」。
落地时有两个选择，我先想的是拿基准周比 —— **那是错的**：

| 比对量 | 问题 |
|---|---|
| 基准周 | 单次求解 20 s，机器一忙就落到 `FEASIBLE`，而**那个状态按 §3.11.1 不保证逐字节可复现**。拿它当门禁 = 一个会飘的判据，而会飘的门禁比没有门禁更糟（它教人重跑） |
| **40 个黄金用例**（选定） | 全部落在 `OPTIMAL`/`INFEASIBLE` 两种**可复现终态**，实测 10.7 s 跑完，聚合成一个数 |

指纹的定义：逐用例取 `content_sha256`（`INFEASIBLE` 的记字面量 `INFEASIBLE`——
不可行同样是确定性结论），**按用例名排序**后拼接再 sha256。排序是必须的，
字典序不定就不可复现。

⚠️ **40 个里有 2 个设计上就是 `INFEASIBLE`**（`g29_airspace_closed` /
`g38_closure_plus_runway`，空域整周关闭本来就排不出班）。第一版把它们当失败，
于是这个工具**永远返回 1**。

**compose 那一侧的形态也是被实测逼出来的**：schedule 环境 8.5 GB，烤进镜像意味着
「镜像里那套」与「裸装那套」**不是同一个环境** —— 而出口标准要比的恰恰是
「两条路径跑出同一个结果」，那时比出来的差异说明不了任何问题。改成 bind-mount
宿主同一份环境与代码（挂在**相同绝对路径**，conda 的 shebang 与编译产物写死了
绝对路径），比对的才是「部署方式」这一个变量。

基础镜像也不能拉：本机 `/` 只剩 26 GB 且 `docker pull ubuntu:20.04` 在这个网络下
拉不动。`build_base_image.sh` 改为从宿主自身抽 glibc 闭包 `docker import`，
**产物 6 MB**，且兼容性是由构造保证的而不是靠「发行版版本号看起来对得上」。

### 3.3 ★ 审计的四要素，以及两处刻意不做的事

**不做一**：**不采信 `X-Forwarded-For`**。那个头客户端能随便写，采信它等于
让审计日志可伪造 —— 而可伪造的审计日志不如没有。裸装部署里 uvicorn 直接面向
内网，`request.client.host` 就是真实来源。

**不做二**：**GET 一律不写审计**。读操作留痕只会把表撑到没人愿意翻，
真正要查的那几行反而淹掉。

`diff` 单独存一列，形式上冗余于 `before`/`after`，存它是为了两件事：
管理员不必自己对着两坨 JSON 找不同；以及 **diff 是写入当时算的**，
日后算法改了历史结论也不会跟着变。审计表只追加不更新，冗余在这里是特性。

⚠️ **`after` 必须沿用 `before` 的整套键**，只改真正变了的那几个。第一版只放
决策字段，于是 `value_diff` 把 before 里其余的键全算成 `removed` ——
审计行读起来像是「批准把快照和方案都删了」。

⚠️ **黑板上方案的键是 `solution` 不是 `plan`，求解状态在 `solver_stats.status`
而不是顶层 `solver_status`**。按后者写的第一版，审计行里 `plan_id` 恒为空、
`sorties` 恒为 0 —— 而那看起来完全像「这次运行确实没有方案」，不像 bug。

### 3.4 ★ 模型完整性的「双重校验」指两个时机，不是两套算法

v6 §11.5 写的是「`healthcheck.sh` 与应用启动时双重校验 SHA256」。很容易做成
两份各写各的实现 —— 一段 shell、一段 Python。那样做的结果是**两边算法一旦分叉，
其中一边就变成橡皮图章**：一个算 manifest 的 sha256、另一个算 blob 的，谁都不
报错，而模型被换掉时两边都放行。

所以只写一次（`backend/core/integrity.py`），`healthcheck.sh` 通过
`python -m backend.core.integrity --require` 调它。**测试里钉死了这一点**：
体检脚本里不许出现 `sha256sum`。

两个「不许放行」的边界：**模型文件不在 = 失败**（不是「没什么可比就放行」，
那是最经典的假绿）；**在用 Ollama 却没配 digest = 失败**（不知道该比什么，
等于这道防线不存在）。`mock`/`replay` 两态整体跳过 —— 那两条路一次都不碰
Ollama，拿一个用不上的 digest 卡住 CI 启动只会制造假红。

### 3.5 ★ wheels 有 ABI tag，装错 Python 小版本的报错与真实原因毫无关系

真断网安装第一次跑到 ④ 就炸了：

```
⚠️  conda 本地包缓存不足以离线建环境，回落到 venv（依赖仍全部来自 wheels/）
✅ venv 已建：…/.venv（解释器 Python 3.14.6）
ERROR: Could not find a version that satisfies the requirement aiohttp==3.14.3
ERROR: No matching distribution found for aiohttp==3.14.3
```

**根因不是 aiohttp**：`wheels/` 里的编译包带 ABI tag（`cp311`），而 venv 回落
抓的是 conda **base** 的 Python **3.14**。报错完全看不出真实原因。

修法两步：① `build_package.sh` 把 wheels 对应的版本记进 `conda/PYTHON_VERSION`；
② `install.sh` **按版本挑解释器**（`python3.11` on PATH → conda base →
conda 各环境 → `python3`），挑不到就**明确失败并给三条出路**，
绝不拿一个不匹配的凑合往下装。

⚠️ 顺带发现一件交付面的事：**这台机器的 conda 缓存里没有 `python-3.11` 包**，
所以包里也带不出去。`build_package.sh` 现在会把这件事**大声说出来**
（「目标机必须自带 Python 3.11」）。见 §9.2 第 1 条。

### 3.6 ★ install.sh 把交付包自己写坏了

第一版 `CONDA_PKGS_DIRS="$PKG_ROOT/conda/pkgs"` —— conda 会把包**解压到列表里
第一个可写目录**，于是交付包里凭空多出 **5611 个解压产物**和一个 `cache/`，
`CHECKSUMS.sha256` 当场失效。

**交付包必须是只读的既成事实。** 改成
`CONDA_PKGS_DIRS="$APP_DIR/.data/conda-pkgs:$PKG_ROOT/conda/pkgs"`：
第一项可写（conda 往那儿解压），包内那份只作为只读来源。

修完复验：装完之后 `sha256sum -c` 仍然 952 个文件全过（§5.1 末尾）。

### 3.7 ★ `conda run` 的两个坑，都是静默失效

| 坑 | 症状 | 落点 |
|---|---|---|
| **不转发 stdin** | 构建脚本里的 heredoc 送不进去 → 候选目录列表为空 → 「跳过本地包缓存」被静默打印，包里少 1.5 GB **而构建照样成功** | `build_package.sh` |
| **多 fork 一层** | pidfile 记的是包装进程，`stop_all_app.sh` 杀完**真正的 worker 还活着**（实测在开发机上留下一批孤儿 worker） | `start_all_app.sh` |

两处都改成**直接调环境里的可执行文件**（`$ENV_BIN/python`、`$ENV_BIN/rq`）。

顺带：`start_all_app.sh` 的 worker 自检**不能只数 `Worker.all()` 的长度** ——
Redis 里留着死掉 worker 的注册键，实测数出过 8 个而实际只有 1 个活的。
判据改成「心跳在 60 秒以内」。

### 3.8 ★ 收集类的步骤失败必须像失败

`build_package.sh` 里「收 conda 缓存」那一步第一版是 `else note "⚠️ 跳过"` ——
于是**少收了 1.5 GB 而构建返回 0**。改成 exit 1，并要求想跳过就显式
`--skip-conda-pkgs`。**「我尽力了」不是收集类步骤的合法结局。**

### 3.9 ★ 为验审计动了真库，以及怎么还原的

审计那条出口标准要求「做一次批准操作，贴 audit_log 记录」——这必须是真的
approve。而 `approve` 会在一个事务里推进训练进度、写 `last_done_date` 锚点、

NULL，`plans` 清空，`data/plans/` 的归档产物删掉。

**还原完复验**：`test_api_live.py::test_baseline_week_matches_the_known_result`
单独跑 **1 passed / 20.85 s**，基准周仍是 `OPTIMAL` / 14 架次。

### 3.10 FTS-1002 的构造，比预想的更严一档

出口标准要求「用『新增一条未裁定的语义开关』构造 FTS-1002」。做的时候发现
这道闸**比 v6 字面写的更严**：`REQUIRED_SWITCHES` 那张白名单在**代码**里，
所以

- 往 `semantics.yaml` 加一条没有 `value` 的 `S-14` → 阻断；
- **把 `value` 也填上 → 照样阻断**。

也就是说「只改配置悄悄加一条语义假设」这条路根本走不通，必须去改代码 ——
而那一步会进 code review、会留 git 记录、会被问「业务方哪天裁定的」。
这正是这道闸真正的价值，测试里把两个方向都钉住了。

### 3.11 500 不给 FTS 码这件事沿用 M6 的判断

## 10. 一件事的复盘：真断网这一步值不值

出口标准写的是「找一个干净目录（或干净的 conda 环境）模拟离线安装，**断网**执行
install.sh」。「模拟」两个字给了偷懒的空间 —— 我完全可以只跑 `--no-index` 就说
「全程未出网」，日志里也确实一次 Downloading 都没有。

**真断网（`unshare -rn`）多花了两轮，抓出了三个只有断网才会暴露的问题**：

| 轮次 | 结果 | 抓出什么 |
|---|---|---|
| 第 1 轮 | ❌ 停在 ④ | **venv 回落抓了 conda base 的 Python 3.14**，而 wheels 是 cp311 —— 报错是「aiohttp 找不到」，与真实原因毫无关系（§3.5） |
| 第 2 轮 | ❌ 构建期就红 | 修 ④ 的过程中发现 **`install.sh` 把交付包写坏了**（conda 解压进包，5611 个文件，CHECKSUMS 失效，§3.6） |
| 第 3 轮 | ✅ 八阶段走完，40 个用例全绿，指纹相同 | —— |

**三个问题里有两个在「只跑 `--no-index`」的验证方式下永远不会出现**：
第 1 个要有真实的「本机没有现成环境」情形，第 2 个要真的执行完整个 ④ 阶段。
而这两个都是**离线机上一定会撞到**的 —— 交付现场撞到的代价，是运维对着一个
指向 aiohttp 的报错查一整天。

> **给下一个窗口**：凡是出口标准里出现「模拟」「断网」「干净环境」这类词，
> 先想一想有没有办法**真的**做到。`unshare -rn` 不需要 root，代价只是几分钟。

## 11. CI 上红了一次：构建脚本硬依赖了 conda 环境

**PR #13 第一轮 CI failure**（40m32s）。本机全绿，CI 全红，红的是
`tests/guardrail/test_offline_package.py` 的 8 条：

```
EnvironmentLocationNotFound: Not a conda environment: /usr/share/miniconda/envs/schedule
ERROR tests/guardrail/test_offline_package.py::test_checksums_cover_every_file_and_verify
      - Failed: build_package.sh 失败：
（另 7 条同样）
```

**根因**：`build_package.sh` 用 `conda run -n schedule python …` 解析解释器路径，
**把「有一个叫 schedule 的 conda 环境」当成了硬前提**。而 CI 用的是
`setup-python` 装的解释器，根本没有那个环境 —— 打个交付包这件事其实只需要
「一个装了本项目依赖的 Python」。

**这正是 `CLAUDE.md §6` 那条**：「验证时的视角必须与 CI 的视角一致」。
我在本机把构建跑了四五遍，每一遍那个环境都在。

**修法三处**：

1. **ENV_BIN 回落到 PATH 上的 `python3`**，conda 环境只是优选项；
2. **`environment.yml` 没有 conda 环境时合成一份**（只钉 Python 版本，依赖交给
   `wheels/`），且**文件头写明它是合成的**，不伪装成 conda 导出的；
3. **`conda/PYTHON_VERSION` 移出 `--skip-conda-pkgs` 分支** —— 它与「有没有
   conda 缓存」无关，而跳过大件正是最常用的打包姿势。

**还有一个更隐蔽的**：第一版加了回落逻辑却仍然红，且**日志全空、exit 127**。
`set -euo pipefail` 下 `conda run` 失败会让整条管道失败，而命令替换的失败
**在那一行就把脚本杀掉了** —— 回落代码一行都没跑到。末尾补 `|| true` 才生效。

**复现 CI 视角的办法**（本机就能做，不必等 CI）：

```bash
env -i HOME="$HOME" PATH="<env>/bin:/usr/bin:/bin" FTS_RELEASE_DIR=/tmp/ci_sim \
  bash deploy/offline-package/build_package.sh --skip-wheels --skip-models \
       --skip-images --skip-conda-pkgs
```

`env -i` 清掉全部环境变量（含 `CONDA_PREFIX`），PATH 里只留解释器与系统目录。
两种视角都验过：**「conda 在但没有那个环境」** 与 **「conda 根本不在 PATH 上」**。

**并且把这一课钉成了测试**：`test_builder_works_without_a_conda_env`
用一个不存在的环境名把 CI 的视角复现出来，构建必须 exit 0 且**说出**自己
回落到了合成版。另加三条：`PYTHON_VERSION` 任何构建形态下都要有、
解释器版本不匹配时明确失败、**install.sh 不许往交付包里写**。


**PR #13 第 2 轮 CI：✅ success，34m28s，2408 passed / 38 skipped / 0 failed，
覆盖率 91.79%。** 上面四条测试在 CI 上真的跑过了 —— 而它们要防的正是
「本机有那个 conda 环境所以看不出问题」这件事。

## 12. 合并前又红了一次：11 个集成模块一直在 60 s 下靠运气过

**PR #13 第 3 轮 CI failure** —— 而那个提交**只改了 27 行 markdown**。

```
FAILED tests/integration/test_graph_live.py::test_baseline_solution_is_optimal_and_fully_compliant
       AssertionError: assert 'FEASIBLE' == 'OPTIMAL'
```

**同一份代码 34 分钟前刚在 CI 上全绿过**（run `32145032396`，commit `a7d873e`）。

### 先量，后判（`Z-15` 的护栏）

`CLAUDE.md §7` 第 4 条要求「跑出与已知结果不同就停下来」。按 `Z-15` 先量三项：

| 检查 | 结果 |
|---|---|
| `backend/solver/` 在两轮之间的改动 | **零**（`git diff a7d873e..23eff42 -- backend/solver/` 空） |
| 两轮之间的全部改动 | **27 行 markdown**，一行代码都没有 |
| 失败形态 | `FEASIBLE` 而**不是** `INFEASIBLE` —— 是「没证完」，不是「证明了排不出来」 |

三项都指向**不是求解器回归，是预算没送到**。

### 根因：M6 留下的那句话没有被执行

M6 §3.13 修好了 `test_api_live.py`，并在收工报告里写着：

> **给下一个窗口**：凡是在 **module / session fixture 里跑求解**的测试，
> 都要照抄这条。函数作用域的那把盖不到你。

**这句话没有被执行。** M8 收工时全仓库有 **11 个集成模块**符合这个描述，
而**一个都没有**那把预算：

```
test_commit_plan_live.py     test_crosscheck_live.py      test_diagnosis_agent_live.py
test_graph_live.py           test_hitl_live.py            test_memory_live.py
test_report_baseline_live.py test_retrieval_live.py       test_revision_live.py
test_skill_isolation_live.py test_solver_baseline_live.py
```

它们一直在**产品默认 60 s** 下跑 —— 不带 `--cov` 时够用，带上就卡在边缘，
**靠运气过**。CI 跑机忙一点就翻过去。

### 探针实测（两侧都量了）

写了个一次性用例量模块作用域 fixture 真正看到的预算，量完即删：

```
修复前：[探针] 模块作用域 fixture 里：env=None  settings=60.0     ← 产品默认
修复后：[探针] 模块作用域 fixture 里：env=300   settings=300.0    ← Z-23 的插桩预算
```

**这比「我认为是预算问题」硬得多** —— 它是两个测出来的数。

### 修法：一份 conftest，不是 11 份拷贝

新建 `tests/integration/conftest.py`，**包作用域 + autouse**：

- **包作用域高于模块作用域**，所以它一定在任何 module fixture 之前建立
  —— 那正是 `tests/conftest.py` 那把函数作用域的做不到的事；
- **一份定义覆盖整个目录**，第 12 个模块不必再记得抄一遍
  （11 份拷贝的结局就是这次这样）。

**判据一个字没改**：14 条硬约束、三态、`OPTIMAL` 断言原样；
**产品默认仍是 60 s**（`Settings.SOLVER_TIME_LIMIT_S`）。变的只是让
`Z-23` 已裁定的插桩预算真正送到这些模块的求解上。

复验：`pytest tests/integration/test_graph_live.py --cov=backend` → **14 passed**；
全量 `pytest --cov` → **2436 passed / 0 failed**，覆盖率 **92.01%**。

> **但没有把它变成一道会自己生效的机制**。一句写给下一个人的提醒，
