## 3. ★ 契约测试抓到的真 bug：带时区的时刻会 500

schemathesis 按 `SchedulePlan` 的 JSON Schema 生成载荷时，构造出：

```json
{"takeoff": "00:00:00Z", "landing": "00:00:00.000001Z", ...}
```

Pydantic 把它解析成**带 tzinfo 的 `datetime.time`**，随后 `Sortie._time_consistency`
拿它与朴素的 `TRAINING_WINDOW_START` 比较：

```
TypeError: can't compare offset-naive and offset-aware times
```

**本该是一条 422 契约错误，实际是 500。** 修复落在字段层（`schemas/plan.py`）：

```python
@field_validator("takeoff", "landing")
@classmethod
def _naive_time_only(cls, value: time) -> time:
    if value.tzinfo is not None:
        raise ValueError(f"时刻不得带时区偏移（本场当地时间），实际 {value!r}")
    return value
```

选择在字段层挡下、而不是在比较处补 `try/except`：**带偏移的时刻在本领域里没有意义**
（全系统按本场当地时间记时），越早拒绝越好。这条改动不改变任何合法输入的行为，
既有 1000+ 用例无一受影响。

> **给下一个窗口的提醒**：M4 写真的 HTTP API 时，`SchedulePlan` 会直接出现在请求体里。
> 这条修复保证畸形时间进来是 422 而不是 500。**别把它当多余的校验删掉。**

## 6. 关键决策与理由

### 6.1 「格式校验通过率」的分母是 97 不是 200

200 个场景里 **103 个是 INFEASIBLE，没有方案可导**，把它们算进分母等于白送 103 个通过。
分母取 97 个出解场景，与 M2-C 的 `format_pass_rate` 口径一致。

方案取自 `reports/M2C_200场景运行结果.json` 的 `plans` 段（M2-C 落盘的原样方案），
**没有重解一遍**：M3 新增的是报告层，重解要 69 分钟且按铁律 9 会得到同一批方案，
对本窗口的结论没有增量。这个取舍写在 `tests/scenarios/format_suite.py` 的模块文档里。

### 6.2 为什么写两遍 xlsx

区块2 末行有一格「产物回读层」。第一遍写出时闸门3 还没跑，填 ✅ 就是报告一个未计算的
结果（铁律 6），所以第一遍填「待回读」；第一遍回读通过后重渲一遍填 ✅，**再回读一次**，
确认交付出去的这个文件本身也通过。两遍的差异只在那一格，而它不参与反解。

### 6.3 区块3 的「本周应排」是展示口径，不是判定

`minimum_required()` 按 v6 §3.5.3 的通式（D-4 + S-12）算「满足滑窗所需的最少次数」：
锚点缺失 → 首次截止日 `freq_days − 1`；有锚点 → `max(0, freq_days − gap)`。
A 类 freq=3 → 2 次，B~F 类 freq=7 → 1 次，G/H 类 freq=14 → 0 次，与 v6 §10.4 的示例一致。

**它不是第三套约束实现**：校验器判的是「任意连续 `freq_days` 天窗口内 ≥1 次」，
这里算的是满足它所需的最少次数，两者不会打架。

**先修未满足的组合写 0**：这类组合按约束13 被排除（§3.6），本周对它没有要求。
第一版写成「应排 1 / 欠账 1」，一眼看去像 Tier 0 下欠了 6 笔账 —— 已改正，
并加了回归 `test_block3_does_not_charge_debt_to_blocked_combinations`。

### 6.4 复训行按「类别」合并

区块3 的复训行按 `(人, 类别)` 合并成一行（`missionC-1 / missionC-2（C 类复训）`），
因为 **S-11 的粒度是类别**（Z-8）。逐门列会把「本周应排」算成 2 次，与校验器的口径对不上。
普通进度行仍按 `(人, 课目)`。

### 6.5 版式基准的两条硬取舍

- **image 4 是四张图里唯一的真 Excel 截图**（可见列标 A~E 与选中框），所以 Excel 级排版
  以它为准；image 1~3 是网页渲染稿，只采信信息结构。
- **业务方裁定不着色**：类别底纹与 A 类红字下划线都不做，正文一律黑字白底。
  唯一保留的底纹是 Sheet 4 区块标题行的 `#DDEBF6`（v6 §10.4 强制项，与版式图无关）。
  实测色板保留在抽取清单 §1.4，日后要恢复直接取用。

### 6.6 集成用例的求解预算给到 240s（不是放宽断言）

**这是本窗口踩到的一个坑，写清楚免得下一个窗口重踩。**

第一次跑全量门禁时，`tests/integration/test_report_baseline_live.py` 的两条用例红了：

```
FAILED test_baseline_week_matches_the_m2a_measurement - AssertionError: assert 'FEASIBLE' == 'OPTIMAL'
FAILED test_same_inputs_reproduce_the_same_plan       - AssertionError: assert 'a77acefb65fc…' == '585df4c13281…'
```

**同一个根因**：基准周在开发机上 18~21s 解完，**叠加 coverage 插桩后顶出了 30s 默认预算**，
落到 `FEASIBLE`；而 v6 §3.11.1 明说 `FEASIBLE` 既不保证最优、也不保证逐字节可复现
（被预算截断的求解切在哪一步取决于机器当时有多忙），于是第二条也跟着红。
单独跑（不带 coverage）两条都是绿的。

处理方式沿用 **M2-D 对 `test_baseline_is_byte_reproducible` 的同一处理**：把本模块的求解预算
显式给到 **240s**。**断言一个字没放宽** —— 状态仍须 `OPTIMAL`、架次仍须 14、两次求解的
`content_sha256` 仍须逐字节相同；改的只是「给求解器多少时间把最优性证完」，证完立刻返回，
快的机器上一秒都不会多花。「默认 30s 够不够」由 `test_solver_baseline_live.py::test_baseline_week_is_optimal`
单独把关，那条用例仍然用默认预算。

> **判据**：一条用例如果同时依赖「预算够」和「被测性质」，就会得到与被测性质无关的偶发红。
> 拆开 —— 预算够不够单独一条用例验，其余用例给足预算。

## 7. 已知限制 / 给下一个窗口的前置条件

1. **基准周排不出复训架次**（刘斌的复训窗口跨出 W02），所以「刘斌训 / (AC84/复训) /
   区块7 复训标记」这三处呈现由**手工构造的复训架次**覆盖（`tests/fixtures/report_bundle.py`），
   不是连库跑出来的。M4/M5 若造出跨周场景，建议补一条连库用例。
2. **`prompt_versions` / `skill_version` 在 manifest 里是 `null`** —— M4 的 Harness 才有实体。
   **不要为了「字段齐全」去填一个假的 `v1`**；`missing_reproducibility_fields()` 刻意不检查它们。
3. **`solver_log.txt` 默认是一行说明**：CP-SAT 日志要在求解时开 `capture_log`，
   M2-A 实测开着它跑会慢约 50%。要真日志就在调用方开，`ReportBundle.solver_log` 传进来即可。
4. **区块5 的「利用率」是展示统计**，分母口径写在 `_block5_rows` 的 docstring 里
   （飞机按 7 天 × 可用窗；人员按约束11 的周上限；空域按 容量 × 7 天 × 训练窗）。
   它不参与任何判定，**别拿它当验收指标**。
5. **`ReportBundle` 要求 `ctx.week_start == plan.week_start`**，否则构造即报错 ——
   报告里摆错位的事实比不摆更危险。
6. **归档目录默认 `data/plans/`（`Settings.PLANS_DIR`）**，`.gitignore` 已排除；
   测试一律传 `root=tmp_path`，不要往真目录写。
