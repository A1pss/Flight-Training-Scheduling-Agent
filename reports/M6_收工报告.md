## 3. 关键决策与理由

### 3.1 ★ 第 16 个错误码 `FTS-4005`（业务方 2026-08-18 裁定）

v6 §9.2 要求「每个 (tenant, week) 加 Redis 分布式锁」，而 §9.3 的 15 个码里**没有**
「锁被别人持有」。三个选项摆给业务方后选定新增一码：

| 选项 | 后果 |
|---|---|
| **新增 FTS-4005**（选定） | 要改 v6（`Z-24` 已回填）；语义干净，前端能直接说「谁在排、还剩多久」 |
| 复用 FTS-3004 | 不改文档，但前端会提示「数据变了要重解」——**而数据没变** |
| 不给 FTS 码 | 破坏 §9.3 的 `ErrorResponse` 契约，契约测试里会出现一类无码错误 |

固化属性：`WARN` / `stage=solve` / `retryable=True` / HTTP 409，
`details` 必带 `lock_key` / `holder` / `ttl_s`。

**我一并把「运行不在可决策状态」也归到这个码下**（对一个还在求解的运行按确认）：
两者是同一族语义——「现在不能做，等状态变了再来」，同样的 WARN/retryable/409，
用户的下一步都是等。分两个码只会让前端写两遍同样的提示。这一句已写进 v6 §9.3 那一行
与 `Z-24` 的说明块，**属于我对码的适用范围所做的判断，不是业务方原话**。

### 3.2 ★ 两把锁：`(tenant, week)` 之外还要一把 `snapshot_id`

M5 §9.1 第 7 条留了一道必答题，并附了真实的 PG 输出：

```
psycopg.errors.DeadlockDetected: deadlock detected
CONTEXT: while deleting tuple (6,51) in relation "training_progress"
[SQL: DELETE FROM training_progress WHERE person_id=%s AND mission_id=%s AND cycle_start=%s]
```

根因是 `training_progress` 是物化视图、**主键不含 `snapshot_id`**（v6 §6.3.2），
`compile_spec` 每次排班按主键 DELETE 再 INSERT。于是：

- 两个人排**同一周** → `(tenant, week)` 锁挡住了，没问题；
- 两个人排**同一快照的不同周** → 周锁互不冲突，两边照样删同一批行 → 死锁。

业务方 2026-08-18 在三个方案里选定「worker 内再加一把 snapshot 级锁」，
**不动 `compile_spec` 这个确定性节点的事务边界**。代价写在明处：同一快照的排班全局串行
（排一周班是分钟级的重操作，不是并发热点）。

**为什么这把锁必须在 worker 里取**：API 进程提交完就返回了，锁要盖住的是**图执行的
那段时间**。落点 `backend/api/worker.py::execute_run`，实测见 §5.4 第二条。

### 3.3 ★ inline runner 与 app 用了两个 store，轮询永远停在 QUEUED

第一版 `InlineRunner` 直接调 `execute_run(payload)`，而 `execute_run` 自己
`build_store()` 连 Redis —— 而测试里的 app 用的是 `InMemoryStore`。**两份状态**：
worker 写 A，轮询读 B。

表现是「求解明明跑完了（14 架次都在），`GET /jobs` 却一直是 `QUEUED`、
`finished_at` 为空」，**没有任何报错**。冒烟脚本第一次跑出来的就是这个。

已改成 `execute_run(raw, *, store=None)`：RQ 路径默认自己连 Redis（那是另一个进程，
本该如此），inline 路径显式传同一个 store。`InlineRunner(store)` 的构造函数强制这件事。

> **这类 bug 的共性**：两条路径各自「正确」，只是指向了不同的实例。M5 §3.4 的
> 「`ask()` 不转发 `reranker`」是同一族——**参数在下游存在、上游忘了传，没有任何报错**。

### 3.4 ★ `RunResultView` 不能直接 `model_validate` 一个 API 响应

`ValidationReport` / `GroundingReport` 带 computed field，`model_dump()` 会把它们吐出来；
两个模型又都是 `extra="forbid"`，于是回构时：

```
ValidationError: 2 validation errors for RunResultView
validation.all_passed            Extra inputs are not permitted
validation.total_checked_items   Extra inputs are not permitted
```

**这与 M4-B 在 `graph/state.py::model_get` 里记的是同一族问题**（那次是 checkpoint
msgpack 往返，这次是 HTTP JSON 往返）。落点 `RunResultView.from_payload()`：
按 `model_computed_fields` 把派生字段剔掉再校验。

E2E 探路时它是**整页崩掉**的形态（Streamlit 把 traceback 画在页面上），
不是一个安静的 500 —— 算是运气好。

### 3.5 ★ `st.dataframe` 的内容不进 DOM

Sheet 4 的「语义开关」在页面文本里**根本不存在**，尽管截图上看得见。
`st.dataframe` 是 glide-data-grid 的 canvas 实现：内容画在画布上，
**选不中、复制不了、E2E 读不到、屏幕阅读器也读不到**。

所有需要被读到的表都改成了 `st.table`（Sheet 1~3、Sheet 4 七区块、求解面板、
违规明细、解释核验表、摄取变更表）。代价是没有排序与列宽拖拽 —— 这几张表最多几十行，
**可读性比交互性重要**；真正要拿去用的产物是归档的 xlsx。

⚠️ 仅「历史计划」那张表还留着 `st.dataframe`（它可能有几百行，且没有断言要读它的内容）。

### 3.6 ★ 决策会开一个新 job_id，前端必须跟着切

`POST /approve` 走的是 `Command(resume=...)`：**trace_id 不变，job_id 是新的**
（它是一次新的执行）。前端点完确认如果还轮询旧任务，看到的是已经终态的
`AWAITING_HUMAN`，界面停在「等人确认」——**而后台已经归档完了**。

E2E 实测踩到：点完「确认并归档」，下载按钮 240 秒都没出现。
落点 `frontend/views/hitl.py::_follow`（切 `KEY_JOB_ID` + 清 `KEY_RUN`）。

### 3.7 ★ 归档类测试必须精确还原库状态

`approve` 在一个事务里做四件事，其中**写 `last_done_date` 锚点**会改变后续测试看到的
基准状态：那个字段一有值，S-12 的「窗口从本周周一起算」就不成立，基准周的频率窗口
跟着变，M2-A 那条 `OPTIMAL / 14 架次` 的断言可能因此变红。

**不能靠 `rollback()`**：worker 用的是它自己的会话并且 `commit()` 了（v6 §9.2 的
「worker 之间不共享事务」正是这个意思）。所以做了 `restored_db(snapshot_id)`：
进度四个字段按值还原、新增的已完成事实行删掉、新建的计划行删掉。
集成测试与 E2E 各用一次，跑完实测 `last_done_date` 非空行数 = 0、`plans` 行数 = 0。

### 3.8 `{id}` 定为 `trace_id`，不是 `plan_id`

v6 §9.1 只写了 `{id}`。决策要走 LangGraph 的 `Command(resume=...)`，而它认 `thread_id`
——本系统里 `thread_id == trace_id`。`plan_id` 在归档**之前**并不能唯一定位一次运行
（修订轮会重算多次），拿它当 URL 段会在最需要恢复的时候找不到 thread。

### 3.9 未预期异常不给 FTS 码，换一个形状

v6 §9.3 的 16 个码全是业务语义，没有一个是「服务端有 bug」。硬挑一个最像的
（比如 FTS-5001）会造成两种真实伤害：查日志时把「Excel 写坏了」和「PG 连不上」
混成一类；以及让 `retryable` 这一位撒谎。

所以 500 返回的是 `{"kind": "internal", "message", "trace_id", "suggestions"}`
——**形状不同**，前端据此分辨。契约测试里出现 500 直接判失败
（`_assert_error_contract` 遇到 `kind=internal` 就 `pytest.fail`）。

**404 / 405 / 415 保持框架原样**（路由层的拒绝，请求还没进业务代码）；
**400 拉回业务契约**——Starlette 在请求体解析不了时自己抛 400 `{"detail": ...}`，
而本 API 的 400 在别处一律是 `ErrorResponse`，同码两种形状会让前端写两套解析。
这一条是契约测试照出来的。

### 3.10 摄取的 `/changeset` 与 `/confirm` 各自重跑一次 `prepare()`

`PreparedIngestion` 是一堆 Python 对象，塞不进 Redis；而进程内缓存在多 uvicorn worker
下是错的（第二个请求可能落到另一个进程）。**上传的文件本身就是唯一的真相**：
存盘到 `data/uploads/{ingest_job_id}/`，每次从盘上重抽。

代价是同一批文件解析两次；收益是整条链路无状态。而这两次解析必然得到同一结果
——`prepare` 是纯函数，否则 `content_sha256` 那套东西根本不成立（铁律 9）。

### 3.11 前端的角色靠本地解析 token，不加第 12 个端点

v6 §9.1 是 11 个端点，加一个 `/me` 就得改设计文档。前端与后端同机部署、读同一份 `.env`
（v6 §11.1 裸装），所以 `TokenTable` 在前端解析出来的角色与后端判定的**必然是同一个**。
它只用于 UI 提示与 T3 的禁用态 —— **真正的鉴权在后端**，UI 那一道拦不住直接打 API 的人，
也不打算拦。

### 3.12 UI 里加了「表单排班」入口

v6 §9.3 的脚注写着「LLM 挂了，用户改用 `/api/v1/schedule` 的表单输入结构化参数即可
继续排班」——那句话要成立，UI 上就得有那个表单。侧栏新增一个 expander，
`use_llm=False` 是这条路径写死的（不是配置项）。

**E2E 也走这条路提交**：它零 LLM、结果确定，把「界面显示对不对」与「模型今天发挥如何」
彻底分开。
### 3.13 ★ 插桩预算盖不住模块作用域的求解 —— 全量门禁上栽的那一次

**症状**：单独跑 `tests/integration/test_api_live.py` 全绿；全量
`pytest --cov` 下两条红：


**根因**：`tests/conftest.py` 那把 300 s 的插桩预算是**函数作用域**的
（`monkeypatch.setenv` + `@pytest.fixture(autouse=True)`），而本模块真正跑求解的是
**模块作用域**的 `baseline_run` fixture。pytest 按作用域从大到小建 fixture ——
模块 fixture 先建，那时候环境变量还没设上。而预算是在 `compile_spec` 那一刻被烤进
`ConstraintSpec.solver_time_limit_s` 的，于是整次求解用的是**产品默认 60 s**。

**探针实测**（我写了个一次性用例量它，量完就删）：

```

函数体里：            os.environ = "300"，                get_settings() → 300.0
```

不带 `--cov` 时 60 s 够用（基准周约 20 s），带上就不够 —— 这正是 `Z-15`/`Z-23`
描述的现象，只是这次**预算根本没送到**。

**修法**：本模块自己加一个模块作用域的 autouse fixture 把预算设上

那一个定义），并在 `tests/conftest.py` 的注释里写清楚它的作用域边界。
**判据一个字没改**：14 条硬约束、三态、`OPTIMAL` 断言照旧；修完全量下
15 项全绿、24 s。

## 8. 给下一个窗口的接口约定

```python
# ── 起服务（三个进程，缺 worker 时任务永远停在 QUEUED）────────────────
export API_TOKENS='tok:P01:director,tok2:P02:scheduler'   # 空 = 全部 401
export FRONTEND_API_TOKEN='tok'
uvicorn backend.api.main:app --port 8000
rq worker --url redis://127.0.0.1:6380 --worker-class rq.SimpleWorker fts
streamlit run frontend/app.py --server.port 8501

# ── 在测试里建一个可注入的 app ───────────────────────────────────────
from tests.fixtures.api_fixtures import build_test_app, DIRECTOR, restored_db
app, store = build_test_app(          # store 要回传：inline runner 必须与 app 共用
    settings=make_settings(PLANS_DIR=tmp_path),
    session_factory=get_session_factory(),
    today=date(2026, 1, 2),          # 「今天」由外部给，链路里不调 date.today()
)
client = TestClient(app, raise_server_exceptions=False)
client.post("/api/v1/schedule", headers=DIRECTOR, json={"week_start": "2026-01-05"})

# ── 归档类测试的护栏 ─────────────────────────────────────────────────
with restored_db(snapshot_id):       # 跑完把进度/事实/计划三样还原
    ...
```

**八条约定，照着用不会踩坑：**

1. **`InlineRunner` 必须拿到 app 那个 store**（§3.3）。`build_test_app` 已经代劳；
   自己拼 app 的话别忘了。
2. **回构 API 响应用 `RunResultView.from_payload()`**，不要 `model_validate`（§3.4）。
3. **`{id}` 是 `trace_id`**（§3.8）。`plan_id` 只在 `/plans` 的返回里出现。
4. **决策会开新的 job_id，trace_id 不变**（§3.6）。轮询要跟着切。
5. **`(tenant, week)` 锁在 API 层取、worker 层放；`snapshot_id` 锁全在 worker 层**（§3.2）。
   新增任何「会刷 `training_progress` 的入口」都要走 worker 那把锁。
6. **前端需要被读到的表用 `st.table`**（§3.5）。`st.dataframe` 的内容不进 DOM。
7. **E2E 的活动页签是有状态的**：Streamlit 的非活动 tab 仍在 DOM 里但 hidden，
   断言之前先 `_tab(page, "…")` 切过去。
8. **`tests/e2e` 需要 chromium**：`python -m playwright install chromium`。
   没装会 skip 并打印原因，不会静默绿。

## 9. 已知限制与待裁决项

### 9.1 已知限制

1. ⚠️ **M5 §9.3 给 W9 的第三条前置没做**：`VECTOR_BACKEND=chroma` + `EMBED_PROVIDER=bge`
   的真机端到端验证。本窗口一次向量检索都没跑 —— API 与前端不碰检索层，
   `/chat` 在 `LLM_PROVIDER=mock` 下走的是规则路由 + 路 A 的 SQL 精确通道。
   **这条前置应该整体挪到 W11**（那时要用真 bge 跑 320 条探针集，顺手就验了）。
   我没有为了「勾掉一条」去造一个与本窗口交付物无关的验证。
2. **不报任何前端性能指标**（首屏时间、rerun 开销、轮询带宽占用）。v6 §8 没有定义
   前端的可测口径，按铁律 5 不自造。唯一贴出来的数是**轮询响应体 190 字节**，
   它有明确的规格依据（§8.1「保持在几百字节」）。
3. **`/chat` 在 mock provider 下会记一条 FTS-4001**（「Planner 未能经 LLM 规划，
   已改用中性默认 SolveIntent」）。这是设计中的降级路径，不是缺陷 ——
   但它意味着 **E2E 没有验证「真 LLM 下的 `/chat`」**。那条链路由
   `tests/integration/test_graph_ollama_live.py`（M4-B）覆盖，本窗口没有扩展它。
4. **摄取端点的 E2E 只到「页面能显示上传/确认表单」**。真跑一次「上传四份 PDF →
   看 Diff → 裁定 X1 → 入库」需要在 E2E 里造一份新快照，而那会与
   `ensure_baseline_snapshot` 争 ACTIVE 快照。摄取管线本身由 M1 的
   `test_ingestion_pipeline_live.py` 覆盖，端点层由契约测试覆盖。
5. **历史计划那张表仍用 `st.dataframe`**（§3.5 末尾）：它可能有几百行，
   且没有断言要读它的内容。
6. **RQ worker 只验过 `--worker-class rq.SimpleWorker`**（同进程执行）。
   默认的 fork 型 `Worker` 没测过 —— 它理论上也能跑（连接都在任务内部建），
   但**没测过的东西不写进文档**（铁律 6），所以 `CLAUDE.md §9` 与 E2E 里都是
   SimpleWorker。M8 做交付包时若要用 fork 型，**先跑一次 E2E 再改那行命令**。
7. **`GET /runs/{trace_id}` 会建一次图**（为了用 `graph.get_state()` 读 `next`）。
   代价是加载一次知识层与提示词表（毫秒级，都是小文件），换来的是
   「还有哪个节点没跑」这件事由 LangGraph 自己算，而不是抄一遍它的规则。
   轮询走的是 Redis，不碰这条路径。
8. **`ingest` 的暂存目录不会自动清理**（`data/uploads/{ingest_job_id}/`）。
   幂等键靠它，删了就等于「同一批文件重传会重新解析」。**W12 打包交付时要给它
   一条清理策略**（按 mtime 或按快照生命周期），现在留着是刻意的。
