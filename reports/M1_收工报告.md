### 1.1 `cycle_start` 做成数据驱动 + 缺失即提问（本窗口后期重做）

第一版把 2026-01-05 写成了 `loader.DEFAULT_CYCLE_START` 常量 —— 那意味着**换一批
数据就要改代码**，业务方随后明确否掉了这个形态。现在的实现是**两级来源 + 一条
提问路径，没有静默默认值**：

| 来源 | 形态 | 结果 |
|---|---|---|
| ① 文件 | 课目表的「课程开始日期」列（六种列名别名，逐行读，各门课目可不同） | 直接用，**不问、不改代码** |
| ② 对话/命令行 | `--cycle-start YYYY-MM-DD`（W9 的 UI 表单同理） | 用它 |
| ③ 都没有 | 生成 `OpenQuestion`（`Q_cycle_start`），**人工确认门禁拒绝放行**并把中文问题抛给用户 | CLI 退出码 3 |

关键实现点：

- 新模块 `backend/ingestion/questions.py` —— `OpenQuestion` / `QuestionAnswer`。
  它与 `Conflict` 是两个概念：冲突是「两个来源打架、选一个」，问题是
  「必需的值没人给、请直接给」。两者都进 ChangeSet、都会阻断落库。
- `gate.review()` 增加第 3 条硬性判定：**有问题未答（或答案不合法）就拒绝**，
  并把问题原样放进 `GateDecision.pending_questions` 交给 CLI / UI 展示。
- `loader.resolve_cycle_start()` 是最后一道闸：两级来源都没有就抛
  `IngestionError`，**绝不编日期**。
- **`Settings` 里刻意没有 `DEFAULT_CYCLE_START`** —— 加一个默认值配置就等于给
  「悄悄填一个日期」开了后门。
- `--baseline` 仍能非交互重跑：答案来自 `questions.BASELINE_ANSWERS`，
  与 §5.5 的 `ADJUDICATIONS` 同一口径（**已经问过、业务方已经答过**的记录在案）。
  换一批新数据、冒出没登记过的问题，照样会问。

三条路径的实测见 §5.11。

| LangGraph（4） | `checkpoints` / `checkpoint_blobs` / `checkpoint_writes` / `checkpoint_migrations` |

**两个关键设计决策：**

1. **事实表按 `(自然主键, snapshot_id)` 复合主键建模，外键一并复合。**
   理由：铁律 9 要求「同 snapshot_id + 同 ruleset_version + 同 semantics_version +
   seed → 逐字节可复现」，也就是说下游每次查询本来就必须带 snapshot_id 过滤。
   写进主键后多个快照可以共存，Diff 层与 FTS-3004（HITL 恢复时快照已变更）才有
   真实的比对对象。
   **唯一例外是 `training_progress`** —— v6 §6.3 给的主键是
   `(person_id, mission_id, cycle_start)`，任务书要求「字段严格照 §6.3」，故原样照做，
   另用外键把它挂回 `persons` / `missions`。

2. **LangGraph checkpoint 表单独一个 revision，调 `PostgresSaver.setup()`，不用 autogenerate。**
   它自带内部迁移（版本号记在自己的 `checkpoint_migrations` 表里），用 Alembic 去描述
   等于把 schema 演进权抢过来，升级 langgraph 版本必然打架。回滚按依赖反序 drop。

**回滚实测**：`upgrade head → downgrade base → upgrade head` 往返干净，
`downgrade base` 后 public schema 只剩 `alembic_version`。

## 3. 关键决策与理由（**踩过的坑都在这里**）

### 3.1 ⚠️ Chroma client 必须在嵌入模型加载**之后**创建，否则进程直接 segfault

**本窗口最大的坑，也最没有征兆。** 第一次跑 `--baseline` 时进程
`Segmentation fault (core dumped)`，**没有任何 Python traceback**，
`PYTHONFAULTHANDLER=1` 也打不出栈。

逐步二分复现出来的最小组合是：

```
先 chromadb.PersistentClient(...)  →  再 SentenceTransformer(...)   ⇒ segfault
先 SentenceTransformer(...)        →  再 chromadb.PersistentClient(...) ⇒ 正常
```

chromadb 与 torch 各自带的原生运行时在同一进程里初始化会打架。
`upsert_chunks` 因此改成**先把全部向量算完，再建 client**：

```python
# ① 先算向量（此时进程里还没有 Chroma 的原生运行时）
vectors = {name: emb.embed([c.text for c in items]) for name, items in grouped.items()}
# ② 再建 client / collection
api = client or build_client()
```

**这两步的顺序是功能性要求，不是风格偏好，改回去会当场崩。** 已写进函数文档。
调用方若自己传 `client`，同样要保证它是在嵌入模型加载之后创建的。

### 3.2 ⚠️ v6 §6.1 的递归 CTE 原文在 PG 上跑不起来，需要两处修改

原文 `ARRAY[mission_id] AS path`，而 `mission_id` 是 `VARCHAR(16)`：
非递归项类型是 `varchar(16)[]`，递归项拼接后退化为 `varchar[]`，PG 直接报

```
recursive query "prereq_chain" column 5 has type character varying(16)[]
in non-recursive term but type character varying[] overall
```

改成 `ARRAY[mission_id::text]` / `c.path || p.mission_id::text` /
`NOT p.mission_id::text = ANY(c.path)` 才能跑。另外加了 `snapshot_id` 过滤 ——
事实表按快照作用域建模，不带过滤会跨快照连边。**两处都是必要修正，不是风格改动**，
已在 `PREREQ_CHAIN_SQL` 上方注明。

### 3.3 X2 的因果链：修复层的步骤顺序决定第 5 条正则是否是死代码

`aircraft.pdf` 适配课目列的**原始字节是 `missionC-\n1`**，不是字面的 `missionC1`。
`missionC1` 是「行尾连字符断词拼接」这一步产出的中间形态，再由 TOKEN_PATTERNS
第 5 条还原成 `missionC-1`。所以修复层的顺序是：

```
① 全半角归一(NFKC) → ② 中文间换行删 → ③ 行尾连字符断词拼接
→ ④ 拉丁/数字 token 跨行拼接 → ⑤ TOKEN_PATTERNS 五条 → ⑥ 分隔符归一
```

**③ 必须在 ⑤ 之前。** 顺序反过来（先做 ④ 的通用拼接）会直接得到 `missionC-1`，
`missionC1` 这个变体永远不出现，**第 5 条正则就成了死代码**，下次真出现
`missionC1` 反而没人兜。实测取证见 §5 的 X2 一条。

③ 的正则**刻意收窄**为 `(?<=[A-Za-z])-\s*\n\s*(?=\d)`（字母+连字符+换行+数字）。
写成通用的 `-\n` 会把 `2026-01-\n09` 拼成 `2026-0109`。

④ 是必须的补充：v6 五条正则只认 `mis` / `mission` / `mi` / `ssion` 四个切点，
覆盖不到真实 PDF 里的 `missi|onB-1`、`missio|nH-1`、`2026|-01-07`。

### 3.4 全半角归一化统一到**半角**（NFKC），规则切分正则同时接受两种宽度

`rules.pdf` 原文用的是半角括号（`约束1(时间一致性)【硬约束】`），而 v6 §5.3 给的
切分正则写的是全角 `（）`。选择用 NFKC 归一到半角（`（`→`(`、`１`→`1`、
`　`→空格），`、。【】≥` 这些没有半角等价物的字符原样保留 —— `≥` 活下来很关键，
频率解析依赖它。

`RULE_RE` 写成 `[（(]` / `[）)]` **同时接受两种宽度**：只放宽匹配面，切分单元
仍是「单条约束」。这是对 v6 §5.3 正则字面的一处偏离，**列在这里等你确认**。

### 3.5 Diff 的基线取快照存档，不取事实表回读 —— 为此给 `data_snapshots` 加了一列

第一版让 Diff 拿「事实表回读」当基线，结果每次摄取都凭空多报 **14 条「新增规则」**。
原因：`rules.pdf` 的条文原文按 v6 §6.1 **只进 Chroma、不进 PG**
（PG 侧的 `rulesets` 存的是 YAML 规则集的版本登记，不是 PDF 条文），
从事实表永远拼不出 `rule` 那一类。

修法：`data_snapshots` 加 `normalized_facts JSONB`，存 `normalize_facts()` 的完整输出，
Diff 以它为基线。这样 Diff 精确，规则原文的变更也才会真的走到人工确认门禁。
`load_normalized_from_db()` 保留下来专做「写进去的 = 读出来的」往返自证（集成测试用）。

**这一列是我在自己这个 revision 里加的（未合并过，没有历史包袱），不是第二个迁移。**

### 3.6 parser 绝不裁决冲突，裁定值由门禁应用

§5.5 X1 明令「不要在 parser 里悄悄选一个」。所以：

- `personnel.py` **两侧都如实记下来**：明细表的 2026-02-07 落进
  `qualification.expiry_date`，总表原文留在 `recurrent_due_raw`
- `conflicts.py` 检出并给出 `adjudicated_value`（**建议值**）
- `gate.py` 判定裁决合法性，**裁决值与 §5.5 裁定表不符就拒绝**，除非显式
  `override_adjudication=True` 且给出理由（理由进审计日志）
- `pipeline.commit` 才真正改值，并因此**重算 snapshot_id**
  （`snap_001c16b0c786` → `snap_9724982865ee`，内容变了 id 必须跟着变）

**副作用（正确但需要知道）**：每次重新摄取同一批 PDF，X1 都会重新浮出来，
Diff 会显示 `person/P04 MODIFIED (qualifications)`。这不是 bug —— 冲突是真实存在的，
每次都该让人重新确认一次。集成测试
`test_diff_against_committed_snapshot_is_empty_except_x1` 把这个行为钉住了。

### 3.7 `--baseline` 不是绕过人工门禁

门禁的全部判定逻辑照跑，只是把「按裁定选 2026-01-07」这个动作从人手里换成了
`ADJUDICATIONS` 那张版本化裁定表，批准人记为 `baseline(v6 §5.5 裁定表)` 并进
`audit_log`。理由：基准快照必须能非交互地逐字节重跑（铁律 9）。
**任何未裁定的冲突都不会被自动放行** —— `baseline_resolutions` 只给已裁定的冲突
生成裁决，其余留空，门禁会拒绝并列出待裁项。

### 给你铺好的接口

### 8.2 规则切分正则同时接受全角与半角括号 —— 请确认

v6 §5.3 给的是 `约束(\d+)（(.+?)）【(.+?)】`（全角括号），而 `rules.pdf` 原文用的是
**半角**括号。修复层 NFKC 归一化到半角后，正则写成 `约束(\d+)[（(](.+?)[）)]【(.+?)】`
两种宽度都接受。**只放宽匹配面，切分单元仍是「单条约束」，14 条一条不差。**

### 8.3 `cycle_start` —— 已按追加要求改成数据驱动，无需再拍板

原先列在这里的风险（推定值进主键、换数据要改代码）**已经消除**，见 §1.1：
文件里有就用文件的、没有就问用户、绝不静默默认。当前基准快照的 2026-01-05
来自一条**有署名有日期的回答记录**，不是代码里的常量。

仍需知道的一点：`training_progress` 的主键 `(person_id, mission_id, cycle_start)`
**不含 `snapshot_id`**（v6 §6.3 原文如此），所以同一 (人, 课目, 周期起点) 全库唯一，
两个快照没法各存一份。这正对应它「物化视图」的定位 —— 物化时按主键清旧行，
只保留最新一次的结果。**如果哪天需要多快照并存的进度表，得改 v6 §6.3 的主键定义。**
