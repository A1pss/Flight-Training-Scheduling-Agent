## 4. 五件实测撞出来的事（下一个窗口最该读这一节）

### 4.1 一次通过率强烈依赖「场景怎么渲染成提示词」（`Z-36`）

§12.5.1 定义了指标和方法，**没定义这一步**，而它决定数字：

- **口径 A**：把 `expected_params` 渲染成中文任务陈述（值给了，字段名不给）→ **99.50%**
- **口径 B**：原样用数据集的 `prompt_context`（模型拿不到任何取值）→ **66.83%**

> **报任何一次通过率都必须标明口径。** 两个数不可混用、不可平均。
> 硬地板 x 也随口径变：口径 A **0.00%**、口径 B **26.67%**。

**两个口径测的都不是生产形态**，这一点要说清楚：A 是照抄（任务标题就是工具自己的
`description`，工具选择正确率 100% —— 它没在「选」）；B 里那句 `prompt_context`
是构造期自述句，生产里没人这么说话，而且**模型在生产里永远不会被要求凭空产出
编号**（图会给 `week_start`、快照摘要，还有三个 `resolve_*` 工具）。
**要测能力就该用 `nl_360` 走真实链路。**

### 4.2 参数精确匹配率 86.5% 那 13.5% 的缺口是假的

逐条查了那 27 条：**全部**是自由文本或嵌套字段不匹配 ——
`propose_solve_intent` 16（`rationale` 自由文本 + `intent` 嵌套）、
`bm25_search`/`vector_search`/`rerank` 11（`query` / `collection` 自由文本）。

一个具体例子：期望 `query="张勇 的训练情况"`，模型给 `query="张勇 的 训练 情况"`
—— **给 BM25 做了分词，工程上更对**，但字符串不等被判成错。

> **想把指标改严（要求「选对工具 + 填对参数」）时，必须按字段类别分开**：
> 实体编号 / 枚举 / 数值 / 布尔**精确匹配**；自由文本**不比对**。
> 否则测的是字符串相等，不是正确性。

### 4.3 模型会自己点 ACL 行之外的工具（`Z-37`）

口径 B 下 Diagnosis 去调了 `resolve_person`（route 的工具），被调用期
`assert_allowed` 拦下报 `FTS-4004`。**口径 A 下一次都没发生**。

> **本窗口在这里踩过一次坑**：runner 原先把「valid 层出现越权」一律当成
> 「ACL 矩阵与数据集漂移，必须当场炸」，于是口径 B 跑到第 89 条崩掉。
> **判错了对象** —— 数据集自身越权由 `ToolCallItem._consistency` 在**加载期**
> 就挡住了，能走到 runner 的只有模型自己越权。现在记成 `acl_attempt`，
> **与五类契约失败分开统计**（越权是权限失败，混一张表会让 §15.2 ⑥ 照着错的
> 分布挑难负例）。

### 4.4 温度 0 下「×3 轮」验的是稳定性，不是方差（`Z-38`）

三轮逐轮一致：口径 A 0.995/0.995/0.995，口径 B 0.665/0.670/0.670。
三轮条目顺序相同，推理端在相同前序状态下给出相同结果。

**同一件事的另一面**：口径 A 那 3 条失败全是**同一条场景**
（`TOOL-VAL-147`，`rerank`，参数含 `ent:person:P08` 这种 `Z-30` 的双 doc id 形态）
三轮重现，但**单独重跑不复现**（裸调 provider 一次、走完整 runner 一次，都过）。

> **不许把 600 当独立样本去算置信区间。**

### 4.5 `estimate_tokens` 高估很多，报告里的 token 必须实测

同一个量：估算器给 **2468**，实测 **1733.7**（高估 42%）；
schema `description` 的可裁量估算 **652**、实测 **324.9**（高估一倍）。

> `harness/tokens.py` 自己就写着「估算用于事前拦截，实测用于事后记账」。
> **凡是要进报告或门禁的 token 数，一律走 `prompt_tokens.py` 的三次差分。**

## 6. 🚑 给 M9-B 的阻塞项：Planner 读不到 `state["week_start"]`

**这条必须在 M9-B 实验一开跑前处理掉，否则那一组三个指标全是脏的。**

### 6.1 现象

`tests/integration/test_graph_ollama_live.py::test_end_to_end_latency_on_the_real_chain`
**失败，且先于本窗口存在**（把本窗口全部改动 `git stash -u` 后在干净 `main` 上重跑，
同样失败）。该测试带 `@pytest.mark.ollama`，**CI 上跳过**，所以 CI 一直是绿的。

```
explanation = 还有几点需要您确认：
1. 请提供您希望进行排班的具体周数（例如：下周、2026年第二周等）。
solver_stats = None
```

`week_start=2026-01-05` 已在 state 里，Planner 仍然追问周次 → 走澄清路径去人工门禁
→ `solve` 根本没跑。

### 6.2 根因（已实测定位到一行）

`backend/planner/intent.py::_planner_blocks`：

```python
summary.update({
    ...
    "目标周": request.iso_week or "（未指定）",   # ← 只读 iso_week
    ...
})
```

实测三种输入渲染出的摘要：

| 输入 | 摘要里的「目标周」 |
|---|---|
| 什么都没有 | `（未指定）` |
| **`request.week_start=2026-01-05`** | **`（未指定）`** ← 有值也读不到 |
| `request.iso_week=2026W02` | `2026W02` |

两个缺口：① `_planner_blocks` 不看 `request.week_start`；
② `state["week_start"]` 根本没往下传 —— `components/planner.py::_first_round`
只把 `_request_of(state)` 交给 `plan_solve_intent`，state 里的周次丢在半路。

**所以当用户的话里没有周次、而周次由结构化入口或上游给进 state 时，
Planner 会看到「（未指定）」并如实追问。模型没做错，是它没拿到那个信息。**

### 6.3 为什么它专门毒害实验一

实验一的主指标把「**正确地反问澄清**」计为成功，硬门禁是**误执行率 ≤4%**，
而**反问阈值要由误执行率反推**。一个会无故反问的 Planner 会同时：
主指标被推高、误执行率被压低、反推出的阈值系统性偏移。

M9-B 的提示词自己写着「一个见谁都反问的系统主指标能刷得很好看」——
**我们现在链路上就有一个。**

### 6.4 建议修法（未实施，等业务方定）

**本窗口没有改 `backend/planner/` 与 `backend/components/`** —— 那是 M4-B 的范围，
混进「M7 基线与评测底座」这个 PR 会让改动面失焦。建议单开 `fix/planner-week-from-state`：

```python
# ① backend/planner/intent.py::_planner_blocks 增加参数与回退链
def _planner_blocks(request, prev_plan, *, user_role, week_start=None):
    week = (
        request.iso_week
        or (iso_week_of(request.week_start) if request.week_start else None)
        or (iso_week_of(week_start) if week_start else None)
        or "（未指定）"
    )
    summary["目标周"] = week


# ② plan_solve_intent 增加 week_start 形参并透传
# ③ backend/components/planner.py::_first_round 从 state 取值传下去
#    week_start=state_get(state, "week_start", None)
```

**三条必须同时满足的约束**（否则会踩别的规格）：

1. **不许给缺失的周次设默认值** —— S-14 / §5.1.1 / `FTS-1004`：缺输入即提问。
   这个修复只做「**已经有的信息要让 Planner 看见**」，三个来源都空时照旧追问。
2. **`week_start` 必须是周一** —— `SchedulingRequest._week_start_is_monday` 已有校验，
   从 state 取的值也要过同一道。
3. **不与 M9-A 的裁定冲突** —— 「缺周次一律归歧义层」说的是**用户这句话里**没有周次；
   周次来自 state 时不属于「缺」。

## 9. 已知限制

1. **`optimized` 配置未跑**（§15.4 消融第三行）。理由：口径 A 下 `zero_shot` 100.00%
   与生产 99.50% 无差别，没有优化空间可测；口径 B 下要优化就得照实测失败模式重写，
   而那张分布表本窗口才第一次拿到。`prompt_configs.OPTIMIZED_SUFFIX` 里现有的五段
   是**按常见失败类型先写的，不是按实测写的** —— 要用先重写。
2. **超预算层的 6 条探针场景是「契约级」验证**，不是端到端。判的是 `ProbeBudget`
   的耗尽契约（`is_exhausted()` 为真、`next_limit()` 归零、全程不抛）。
   端到端那条 `{"status": "BUDGET_EXHAUSTED"}` 载荷路径要一份完整的 `SpecBundle`
   （等于先跑一次 `compile_spec`），不在本 runner 范围内。
3. **`acl_attempt` 计数偏低**（实测 2 次）。首次遭遇时 runner 直接崩了，那条没落盘，
   续跑重跑该条时模型没再重复。
4. **口径 B 的参数精确匹配率不适用**（0.50%）—— 提示词里没有取值，模型不可能猜中。
   报告里标成「不适用」而不是一个 0 分。
5. **端到端延迟本轮不报** —— GPU 部分卸载，那个数是机器状态的函数。
6. **未测的指标一个都没估**：误执行率、意图分类、槽位 F1、修订翻译准确率、
   通用能力回归 —— 全部属 §12.2 / §12.6，是 M9-B 的事。
