## 3. 关键决策与理由

### 3.1 ★ `superseded_by` 原本被当成作废标记，历史时点查询一律返回空

**症状**：时效样本的前半（2026-01-06「刘斌能不能飞仪表课目」）返回不了正确答案。

**根因**：`is_active_at` 原本写成

```python
return item.superseded_by is None  # ← 被取代过就永远不算有效
```

于是「2026-01-05 生效、01-12 被新版本取代」的那条记忆，**在 01-06 这天也查不到**。
而 §6.4 的活样本要的恰恰是「同一问题在两个时点给出不同答案」。

**修法**：有效性**只由区间决定**（半开 `[valid_from, valid_to)`）。
`superseded_by` 是**链接，不是墓碑**。

**唯一保留的严格性**：`superseded_by` 有值而 `valid_to` 为空的行一律判无效 ——
那种行说不清自己什么时候不再成立，八成是有人只改了一半
（写入方 `procedural.put_preference` 是两个字段一起改的）。

### 3.2 ★ 「上上周」被「上周」抢先匹配（既有 bug，M5 实测抓出）

`_RELATIVE_WEEKS` 是个字典，`for phrase in _RELATIVE_WEEKS` 按**插入顺序**扫，
而 `"上周"` 排在 `"上上周"` 前面 —— `"上周" in "上上周"` 为真，于是先命中。

**它不报错**：返回的是一个格式完全正确的 ISO 周，只是差了一周。在检索层
表现为「召回到的是另一周的记录」，排查时看不出任何异常。

已改为按表述长度降序匹配。`tests/unit/test_retrieval_rewrite.py` 六个相对周
表述逐个钉住。

### 3.3 ★ 回显确认：原本是「先重解再展示」，顺序与规格相反

v6 §7.3.4 第 4 条：

> 修订翻译是高风险的语义映射，UI 上先展示「我理解为：……」，**用户确认后才重解**。

**M4-B 的实现**：`planner` 翻译完把回显写进 `state["explanation"]`，
然后**直接 `goto="solve"`**。两个问题：

1. 顺序反了 —— 先解再问，等于「翻译错了也已经排了一版」；
2. `explanation` 归 `explain` 节点所有，每轮末尾被方案解释覆盖，
   **用户根本看不到那句回显**（实测：撤销的回显被「共 14 个架次……」盖掉）。

**改法**（不新增节点、不新增决策枚举）：

```
human_gate(REVISE + 原话) → planner 翻译 → human_gate(展示回显)
                                              ↓ APPROVE
                                            solve → validate → explain → human_gate(展示新方案)
                                              ↓ REJECT
                                            planner 弹栈撤回 → human_gate
```

- 新增黑板字段 `revision_echo`（**不与 `explanation` 合用**）、`pending_revision`、
  `revision_cancelled`；
- `human_gate` 按 `pending_revision` 选路由表：`REVISION_ECHO_ROUTES` 里
  **`APPROVE` 是「去重解」而不是「去归档」**（用户还没看过新方案，此刻归档
  等于跳过 `solve → validate`）；
- 图里给 `human_gate` 加了一条到 `solve` 的边。

**为什么不用 `interrupt()` 直接在 planner 里问**：那会让 `planner_node` 没法脱离
LangGraph 单测（`interrupt()` 在运行时之外抛 `RuntimeError`），而本仓库的节点
一直是「能直接调、能直接测」的（M4-B §节点包装 第 1 条）。

⚠️ **给 M6 前端**：修订轮现在是**两次门禁往返**。第一屏问「我理解对了吗」
（`revision_echo` 非空 + `pending_revision=True`），第二屏才问「这版方案要不要」。
载荷里两个字段都有，UI 据此换文案与按钮语义。

### 3.4 `ask()` 不转发 `reranker`，测试里的替身被静默忽略

`retrieve()` 有 `reranker` 参数，`ask()` 没有，于是 `rerank()` 回落到
`build_reranker(settings)` —— 本机 `.env` 里 `RERANK_PROVIDER=bge`，**真的把
2.2GB 的 bge-reranker 加载进来了**（测试日志里那行 `加载 bge-reranker-v2-m3`
就是证据）。CI 上没有那个权重，会当场红。

已补 `ask(..., reranker=...)` 并让 `RetrievalRig.kwargs()` 带上它。

**这类漏接的共性**：参数在下游存在、上游忘了透传，**没有任何报错** ——
它只是悄悄用了默认值。M4-B 的 `planner_tool_handlers` 漏接是同一族问题
（那次是真机跑端到端照出来的，这次是集成测试的日志照出来的）。

### 3.5 ★ 基准周排不出 JL-9 架次，`PIN_RUNWAY × JL-9` 的图级负例造不出来

出口标准要「对 JL-9 架次下 `PIN_RUNWAY(RWY-2)` 应不可行并按 FTS-3005 回滚」。
实测发现**这个前提在基准数据上不成立**：

| 事实 | 来源 |
|---|---|
| 基准周 14 个架次全部落在 JL-8 上（AC10/27/34/49/61/73） | 本窗口实测，§5.9 |
| 学员只持 JL-8 机型资质 | `person_aircraft_types` |
| 14 个架次全部涉及学员（9 带飞 + 5 单飞） | v6 §1.4 |
| 刘斌持 JL-9，但 C 类复训窗口 `[01-08, 01-14]` 跨出 W02，本周不强制 | v6 §1.2.4 |

所以「把某个 JL-9 架次钉到 RWY-2」这件事，在基准周里**没有可钉的对象**。

**业务方 2026-08-15 裁定：预检层验到即可，不另造 JL-9 数据。**

落地为两条用例：

- **预检层**：构造一个含 AC84 架次的方案，`check_runway_feasibility` 给出
  「AC84 是 JL-9 —— RWY-2 只服务 ['JL-8']」。判据从 PG 读，不是写死那句话。
- **图级不可行回滚**：改用同一个 JL-9 根因、在基准数据上真能触发的构造 ——
  「何超那个换成 AC84」（何超只持 JL-8）→ INFEASIBLE → FTS-3005 回滚。

另加一条用例把这个数据事实本身钉住
（`test_the_baseline_plan_has_no_jl9_sortie_so_the_runway_negative_case_is_pre_check_only`），
免得下一个窗口以为是漏测。

### 3.6 撤销后重解出来的方案，不必与当初那版 v2 逐字节相同

第一版测试断言「undo 两次后方案 == 当初的 v2」，实测**不相等**（AC49 的两个
架次落到了别处）。查下来**这不是 bug，是设计的必然**：

撤销的语义是「去掉那条约束**再解一次**」（第 1 条硬性设计），而目标函数里的
最小扰动项锚定的是**当前**方案（此刻是 v4），不是当初那版 v2。于是求解器给出的
是「满足 v2 那套约束、且离 v4 最近」的解 —— 与当初从 v1 出发解出来的 v2 可以
不同，**两者都是 OPTIMAL**。

这正是「撤销 ≠ 把旧方案取回来」的实际后果。要断言的是**约束集回到了 v2**
（栈深、`round_no`、`constraint_spec.incremental_constraints`），
而不是像素级还原。

### 3.7 语义类答案的事实内容由路 A 出，LLM 只组织语言（业务方 2026-08-14 确认）

v6 §12.4 给语义类 120 条探针的目标是 **≥98%**，并注明「走 SQL 精确通道，
**不依赖模型**」。若答案内容由 14B 生成，那个 98% 就成了模型当天发挥的函数。

**落法**：`structured.py` 产出 `FactAnswer`（确定性代码算出来的结论 + `table`/`pk`
引用），`generate.py` 把它们作为「已核实的事实」放在提示词最前面，LLM 只措辞；
**逐句核验，有一句查无实据就整段退回事实直出**。

于是 M1~M4 四条探针的正确性与 LLM 无关 —— §5.1 那四条就是 `harness=None`
（零 LLM 调用）跑出来的。

### 3.8 三路召回的「互不阻塞」是顺序执行，如实说明

v6 §6.5.2 写的是「多路并行召回（三路，**互不阻塞**）」。**本实现是顺序执行的**：
三路之间没有任何数据依赖，谁先谁后不影响结果，但确实没有开线程。

基准语料规模（**48 篇文档** = 34 条实体摘要 + 14 条规则条文）下三路合计是毫秒量级，引入线程池换来的是竞态与
不可复现的风险，不划算。**「互不阻塞」在这里的落点是「不共享状态、任一路
失败不影响其余两路」，不是并发执行** —— 这条写在 `pipeline.py` 的模块注释里，
不含糊过去。

### 3.9 路 B 与路 C 共用一份语料

RRF 融合的是**排名**。两路排的若不是同一批文档，`1/(k+rank)` 的加和会悄悄
偏向文档多的那一路。所以 `corpus.py` 构建一次，两路各自建索引。

语料三个来源：PG 事实表的实体摘要句、`ruleset_v1.3.yaml` 的 14 条规则条文
（**一条一个文档、不切分**）、`episodic_memories` 的摘要。

**摘要句是索引，不是事实** —— 权威值一律回 PG 取（路 A）。所以本模块的措辞
与 `ingestion/chunkers.py` 的摘要句不必逐字相同，两者都是同一份 PG 事实的索引。

### 3.10 第五个 Chroma collection：`episodic_summaries`

§6.1 那张表列的是**文档**向量的四个落点，没给情景记忆留位置 —— 而 §6.2 明确
要求情景记忆「PG 存权威内容 + Chroma 存摘要向量」。塞进 `historical_reports`
会污染那一路召回：历史报告是排班产物、按周归档；情景记忆是会话经历、按 §6.4
的三个训练周期归档到冷表，两者的时效语义完全不同。

与 M1 单列 `situation_docs` 是同一条理由。

### 3.11 「3 个训练周期」的周期长度取快照里**最长**的 `cycle_weeks`

v6 §6.4 只说「超过 3 个训练周期后归档」，而训练周期按课目类别有 12 / 16 / 20 周
三种（§6.3.3）。本窗口取**最长的那个**（基准数据下 = 20 周 → 归档线 60 周）。

**保守选择**：归档的条目仍可检索，只是不参与默认召回；早归档的代价是
「本该被想起来的事没被想起来」，比晚归档贵得多。

落点 `episodic.retention_cycle_weeks()`，**不是配置项** —— 它跟着数据走。

### 5.6 §6.4 时效性与冲突消解

**同 key 多版本**：写入 tier=1（对话推断）→ 一周后写入 tier=2（排班确认记录，
可信度更高）→ 默认召回返回 **tier=2 + `history_count=1`**；旧行的 `valid_to`
与 `superseded_by` **两个字段一起改**。回到旧版本的区间里查，返回的仍是 tier=1。

**写入冲突三种结局**（实测逐条）：

| 现存 vs 新写入 | 结果 |
|---|---|
| PG事实(01-07) vs 对话推断(02-07) | **reject** —— 不写入但留痕，PG 事实纹丝不动 |
| 对话推断 vs PG事实 | **supersede** —— 旧行让位 |
| 排班确认记录(tier1) vs 排班确认记录(tier3) | **escalate** —— 升级人工，抛 `DataConflictError`（FTS-2001） |
| 值相同（键序不同也算相同） | 不算冲突，不产生新版本 |

**遗忘策略**：60 周前的情景记忆 → `archive_stale_episodes` 归档 1 条；
默认召回只返回「最近」那条，`include_archived=True` 时两条都在。

**蒸馏**：出现 1 次 → 跳过（「一次不算习惯」）；出现 2 次 → 写成偏好
`{"tier": 2, "support": 2}`，来源标 `排班确认记录`（**永远压不过 PG 事实**）；
跑两遍不长出第二个版本。

KNOWLEDGE_MAX_STEPS == 6

outcome.steps_exhausted is True
harness.react_rounds == 6      ← 刚好 6 轮，不多不少

## 8. 给下一个窗口的接口约定

```python
from backend.agents.knowledge import ask  # 问答入口
from backend.retrieval.pipeline import RetrievalConfig, retrieve
from backend.retrieval.corpus import build_corpus
from backend.retrieval.vector import build_vector_index

outcome = ask(
    "何超能不能排 missionB-1？",
    session=session,
    snapshot_id=snapshot_id,
    directory=directory_from_session(session, snapshot_id),
    today=date(2026, 1, 5),  # ← 必传，图里不调 date.today()
    as_of=None,  # ← 不给就取 today；决定时效过滤与「能不能飞」的基准
    harness=harness,  # ← None 即零 LLM，答案照常正确
    corpus=corpus,  # ← 复用语料，避免每次问都重建
    vector_index=index,
    reranker=reranker,  # ← **必须显式传**，否则回落到 settings（§3.4）
    config=RetrievalConfig.from_settings(enable_structured=False),  # 消融用
)
```

**八条约定，照着用不会踩坑：**

1. **`as_of` 决定答案。** 同一个问题在 01-06 与 01-09 的答案不同（刘斌资质）。
   给它一个默认值等于让「今天是哪天」悄悄进入答案，重放时再也复现不了。
2. **`reranker` / `corpus` / `vector_index` 三样在测试里一律显式传**确定性替身
   （`tests/fixtures/retrieval_fixtures.py::build_rig`）。CI 上没有那两个 2.2GB 权重。
3. **路 A 的结论在 `result.answers`，召回的文档在 `result.contexts`。**
   要判定就读前者；后者只是上下文。关掉路 A 时 `answers` 恒为空 —— 这是设计。
4. **`structured_doc()` 是造路 A 文档的唯一入口**，它把 `authoritative` 恒置为 True。
   自己 `RetrievedDoc(...)` 拼一个忘了置位，那条 SQL 精确结果就会掉进 RRF 里
   和一条旧摘要比排名。
5. **修订轮是两次门禁往返**（§3.3）。第一屏 `pending_revision=True` + `revision_echo`
   问「我理解对了吗」，APPROVE → `solve`；第二屏才问「这版方案要不要」。
6. **`revision_echo` 不许写进 `explanation`** —— 后者归 `explain` 节点所有，
   每轮末尾会被覆盖。
7. **写记忆走 `procedural.put_preference` / `episodic.record_*`**，它们自带冲突
   检测与版本化。绕过去直接 `session.add(ProceduralMemory(...))` 会跳过 §6.4 的
   全部机制。
8. **`memory.write` 在 ACL 里只给了 `extract`。** KnowledgeAgent 的七个工具全部只读，
   `knowledge_tool_handlers` 里没有任何写入口 —— 加一个会被 `acl.py` 在注册期拦下。

### 9.1 已知限制

1. **不报任何检索指标。** Recall@5 / MRR@10 / 时效正确率 / 改写增益一个都没算 ——

   torch/chromadb 初始化顺序（`ChromaIndex.build` 已按「先算完向量再建 client」
   写死，**别去动它那两步**）。W9 接 API 时在真机上跑一次
   `VECTOR_BACKEND=chroma` + `EMBED_PROVIDER=bge` 的端到端即可。
5. **`memory.search` 工具的语义记忆那一路目前走 BM25**，不是 PG 精确查询 ——
   精确查询由路 A 在管线里做了，工具这一路是给模型「再查一次」用的补充。
   要更精确的应该调 `sql_query` / `prereq_cte`。
6. **程序记忆的蒸馏只提炼两类**（松弛档偏好、修订表述）。§6.2 还提到「教员排班
   习惯」，那需要先定义「习惯」是什么可测的量 —— 按铁律 5，没定义就不自造。
   `NAMESPACE_INSTRUCTOR` 常量已留好。
7. ⚠️ **`materialize_progress` 不是并发安全的 —— 这条给 W9 看。**

   本窗口误开了两个 pytest 进程同时跑，PG 当场给出：

   ```
   psycopg.errors.DeadlockDetected: deadlock detected
   DETAIL:  Process 1401288 waits for ShareLock on transaction 4148; blocked by process 1401474.
            Process 1401474 waits for ShareLock on transaction 4152; blocked by process 1401288.
   CONTEXT: while deleting tuple (6,51) in relation "training_progress"
   [SQL: DELETE FROM training_progress WHERE person_id=%s AND mission_id=%s AND cycle_start=%s]
   ```

   **触发是我的操作失误，但暴露的性质是真的**：`training_progress` 是物化视图，
   主键**不含 `snapshot_id`**（v6 §6.3.2），`compile_spec` 每次排班都按主键
   DELETE 再 INSERT。两个请求同时排同一个快照 → 两边以不同顺序删同一批行 → 死锁。
