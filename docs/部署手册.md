# FTS 飞行训练排班系统 · 部署手册

**适用版本** v1.0.0 · **交付形态** 全离线内网部署 · **对应设计** v6 §11

> 本手册面向**运维**。业务操作看《用户手册》，账号/规则/数据维护看《管理员手册》。

---

## 0. 先读这一页

| 事实 | 说明 |
|---|---|
| **主路径是裸装，不是容器** | PostgreSQL 16 / Redis 7 / Ollama 全部用户态运行，**不要求 root**。compose 是备选路径，给「现场只允许容器化部署」的情形 |
| **应用必须起三个进程** | API（uvicorn）· **worker（rq）** · 前端（streamlit）。**缺 worker 时任务永远停在 `QUEUED` 且不报任何错** |
| **排班不依赖 LLM** | 没有 GPU、Ollama 挂了、模型没导入 —— 排班能力完整保留（`LLM_PROVIDER=mock`），受影响的只有自然语言交互与解释生成 |
| **装完必须绿灯** | `install.sh` 最后会跑 40 个黄金用例。**不绿就不算装上了**，不要投入使用 |
| **`API_TOKENS` 留空 = 全部拒绝** | 不是全部放行。这是设计行为 |

## 1. 硬件与系统要求

| 项 | 最低 | 建议 | 校验方式 |
|---|---|---|---|
| CPU | 4 核 | 8 核以上 | `install.sh` 第 ① 阶段 |
| 内存 | 16 GB | 32 GB | 同上 |
| **磁盘余量** | **50 GB** | 100 GB | 同上（v6 §11.4 硬要求） |
| GPU | 无（排班不需要） | 24 GB 显存（本地 14B 推理需 ~17 GB） | `nvidia-smi` |
| 操作系统 | Linux x86_64，glibc ≥ 2.31 | Ubuntu 20.04/22.04 | `ldd --version` |
| Python | 由包内 conda 环境提供 | — | — |

> **没有 GPU 不是阻塞项。** 装的时候 `install.sh` 会给一条 WARN，把 `.env` 的
> `LLM_PROVIDER` 设成 `mock` 即可。排班链路一次都不经 LLM（v6 §0），
> 结果与有 GPU 时**逐字节相同**。

**端口**（全部只监听回环或内网，可在 `.env` 改）：

| 端口 | 服务 |
|---|---|
| 5433 | PostgreSQL 16（避让系统 5432） |
| 6380 | Redis 7（避让系统 6379） |
| 11434 | Ollama |
| 8000 | API |
| 8501 | 前端 |

## 2. 离线安装（主路径）

### 2.1 拿到包之后先校验

```bash
tar -xzf fts-release-v1.0.0.tar.gz
cd fts-release-v1.0.0
sha256sum -c CHECKSUMS.sha256 --quiet && echo "包完整"
```

校验失败**不要继续装**——传输损坏或被改动过的包装出来的系统，出了问题无从查起。

### 2.2 先空跑一遍

```bash
bash scripts/install.sh --prefix /opt/fts --dry-run
```

`--dry-run` 只做**环境体检 + checksum 校验**，不动系统任何东西。体检不过时它会
明确告诉你是哪一项（CPU / 内存 / 磁盘 / conda）。**磁盘余量那一条是硬门槛**。

### 2.3 正式安装

```bash
bash scripts/install.sh --prefix /opt/fts
```

八个阶段，任一失败即停并打印失败阶段：

| 阶段 | 做什么 | 失败常见原因 |
|---|---|---|
| ① 环境体检 | CPU/内存/**磁盘 ≥50 GB**/显存/conda | 磁盘不够；没装 Miniconda |
| ② 校验 checksum | `sha256sum -c` | 包损坏 |
| ③ 铺开源码 | 解到 `<prefix>/FTS_PLANAU` | 目录没有写权限 |
| ④ 建 conda 环境 | `conda env create --offline` + `pip install --no-index` | 包里缺 `conda/pkgs` 或 `wheels/` |
| ⑤ 导入模型 | 拷贝 + **digest 校验** | digest 与 `.env` 里钉的对不上 → 模型被换过 |
| ⑥ 裸装服务 | PG / Redis / Ollama | 端口被占 |
| ⑦ 初始化数据库 | `alembic upgrade head` | PG 没起来 |
| ⑧ **黄金用例** | 40 个场景全绿才算装完 | 见 §6.3 |

装完最后一行会打印 **`golden_fingerprint`**。把它记下来 ——
它是「这台机器跑出来的结果」的指纹，与出厂机上的那个应当**逐字节相同**。

### 2.4 装完必做的两件事

```bash
cd /opt/fts/FTS_PLANAU

# ① 发 token（留空 = 全部拒绝）
conda run -n schedule python -m backend.api.tokens_cli new --user P01 --role director
# 把打印出来的 sha256$... 那一行追加到 .env 的 API_TOKENS

# ② 起应用三进程
bash deploy/native/start_all_app.sh
```

`start_all_app.sh` 起完会**主动去问队列里有没有 worker**。这一步是刻意的：
worker 没起来时系统不会报错，只是所有任务永远排队 —— 用户看到的是「一直在转圈」。

## 3. 日常运维

```bash
# 全栈体检（开工前跑一次）
bash deploy/native/healthcheck.sh

# 起 / 停
bash deploy/native/start_pg.sh      bash deploy/native/start_redis.sh
bash deploy/native/start_ollama.sh  bash deploy/native/start_all_app.sh
bash deploy/native/stop_all_app.sh  bash deploy/native/stop_all.sh

# 只重启某一个
bash deploy/native/start_all_app.sh --worker
```

**日志**在 `<prefix>/FTS_PLANAU/.data/logs/`：`api.log` / `worker.log` /
`frontend.log` / `pg.log` / `redis.log`。全部是 JSON 行格式，每行带 `trace_id`
——排查一次具体请求时按 `trace_id` grep 即可串起全链路。

**`healthcheck.sh` 的退出码就是判据**：0 = 全绿，1 = 有 FAIL。WARN 不影响退出码
（例如「没有 PaddleOCR 模型」只影响扫描件摄取，不影响排班）。

## 4. compose 备选路径

只在「现场只允许容器化部署」时用。**它与裸装路径跑出来的结果逐字节相同**——
这一点由 `deploy/scripts/compare_deploy_paths.sh` 验证，是交付的硬要求。

```bash
cd /opt/fts/FTS_PLANAU/deploy/compose
cp env/prod.env.example env/prod.env      # 按现场填，尤其 FTS_REPO_DIR / FTS_CONDA_ENV_DIR

# 镜像：离线机上不要去拉基础镜像，用包里的或从宿主构建
docker load -i /path/to/fts-release-v1.0.0/images/fts-base.tar
#   或
bash build_base_image.sh

docker compose up -d api worker frontend
```

**镜像里不装任何 Python 依赖**：conda 环境与仓库都是 bind-mount 进去的，
且挂在**与宿主完全相同的绝对路径**上（conda 环境里的 shebang 与编译产物写死了
绝对路径，换挂载点跑不起来）。

容器级 egress 封锁（可选，要 root）：

```bash
sudo bash deploy/compose/iptables_egress_drop.sh apply
sudo bash deploy/compose/iptables_egress_drop.sh status
```

裸装主路径**不需要**它 —— 那条路上 egress 收口在代码层（`backend/core/http.py`
的 allowlist）+ CI 静态扫描 + 运行时抓包三道。

## 5. 升级与回滚

```bash
# 升级：新包解开，装到同一个 prefix
bash scripts/install.sh --prefix /opt/fts
# ③ 会覆盖源码，④ 检测到环境已存在会跳过创建，⑦ 只跑增量迁移

# 回滚数据库一步
cd /opt/fts/FTS_PLANAU && conda run -n schedule alembic downgrade -1
```

⚠️ **`.env` 不会被覆盖**（`install.sh` 只在它不存在时才从 `.env.example` 复制）。
新版本引入的配置项要**手工比对 `.env.example` 补进去**。

⚠️ **升级前先停应用**（`stop_all_app.sh`），否则 worker 会拿着旧代码跑新数据。

## 6. 故障排查

### 6.1 任务一直是 `QUEUED`

**九成是 worker 没起。** 确认：

```bash
bash deploy/native/start_all_app.sh --worker    # 它自己会检查队列上有没有 worker
tail -50 .data/logs/worker.log
```

这个症状**不会有任何错误日志** —— 从系统角度看没有任何东西出错，只是没人干活。

### 6.2 全部请求 401

```
{"code":"...","message":"服务端未配置 API_TOKENS，全部请求一律拒绝"}
```

`.env` 的 `API_TOKENS` 是空的。**这是设计行为**：内网也不给「没配就不校验」这个
后门。用 `tokens_cli new` 发一个。

### 6.3 装到第 ⑧ 步黄金用例不绿

按这个顺序查：

1. `TZ` / `LANG` 与出厂机不同 → 日期字符串变了 → `content_sha256` 跟着变；
2. `SOLVER_SEED` / `SOLVER_WORKERS` 被改过（必须是 42 / 4）；
3. `rules/` 下两份 yaml 的版本串与出厂不一致；
4. 机器负载过高导致求解被预算截断（落到 `FEASIBLE`，那个状态**不保证**逐字节
   可复现，见 v6 §3.11.1）—— 停掉其它重活再跑一次。

单独重跑：

```bash
conda run -n schedule python deploy/scripts/golden_fingerprint.py --per-case
```

### 6.4 启动时报「模型 digest 校验失败」

```
❌ 模型 qwen2.5:14b-instruct-q4_K_M digest 校验失败：digest 不匹配…模型可能已被替换
```

**这是安全机制在起作用，不要绕过它。** 要么模型文件被换过，要么 `.env` 的
`LLM_MODEL_DIGEST` 与包里的模型不匹配。核对包里 `models/ollama` 的来源；
临时可把 `LLM_PROVIDER` 设为 `mock` 让系统先跑起来（排班能力不受影响），
但**必须查清楚模型为什么变了**。

### 6.5 `relation "data_snapshots" does not exist`

数据库没迁移。`conda run -n schedule alembic upgrade head`。

### 6.6 端口被占

`.env` 里改 `PG_PORT` / `REDIS_PORT` / `APP_PORT` / `FRONTEND_PORT`，
compose 路径同步改 `deploy/compose/env/prod.env`。

## 7. 备份

| 对象 | 位置 | 频率 |
|---|---|---|
| **数据库** | `pg_dump -h 127.0.0.1 -p 5433 -U fts fts` | 每日 |
| **排班产物** | `data/plans/YYYY/Www/`（xlsx + json + manifest） | 随数据库 |
| `.env` | 单独保管（含 token 散列） | 变更时 |
| 上传暂存 | `data/uploads/` | 不必备份，可清理 |

`data/uploads/` 的清理策略：**按快照生命周期**——某批上传对应的快照已经不是
ACTIVE 且超过一个训练周期，就可以删。删了的后果只是「同一批文件重传会重新解析
一遍」，不丢任何数据。

```bash
find data/uploads -maxdepth 1 -type d -mtime +90 -exec rm -rf {} +
```
