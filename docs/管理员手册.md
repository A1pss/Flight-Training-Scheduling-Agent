## 1. 权限模型（RBAC 四角色）

| 角色 | 能做什么 | 典型使用者 |
|---|---|---|
| `viewer` | 只读：查任务、查结果、查历史、**下载 xlsx** | 各中队 |
| `scheduler` | viewer + 发起排班 / 会话 / 上传数据 / 驳回方案 | 排班员 |
| `director` | scheduler + **确认归档** + 授权 Tier 3 松弛 | 训练主任 |
| `admin` | 全部 | 系统管理员 |

角色是**阶梯**：高的自动包含低的。端点与角色的对应关系声明在
`backend/api/rbac.py`，**它是可执行的规格** —— 权限矩阵测试按它逐格发真请求，
新加端点忘了写鉴权会在 CI 红。

完整矩阵：

| 端点 | 最低角色 |
|---|---|
| `GET /health` | 匿名（唯一一个） |
| `GET /api/v1/jobs/{id}` `/runs/{id}` `/plans` `/ingest/{id}/changeset` `/schedule/{id}/export` | `viewer` |
| `POST /api/v1/ingest` `/ingest/{id}/confirm` `/chat` `/schedule` `/schedule/{id}/reject` | `scheduler` |
| **`POST /api/v1/schedule/{id}/approve`** | **`director`** |

**第二道门**：`approve` 里如果带了松弛档位，还会**逐档**再核一次
（Tier 3 需 `director`）。**角色够格进这个端点 ≠ 够格批那一档。**

## 2. 账号与 Token

系统用**静态 Token → 角色**映射，不建用户表（全离线内网，没有 IdP）。

### 2.1 发一个新 Token

```bash
conda run -n schedule python -m backend.api.tokens_cli new --user P01 --role director
```

```
── 交给本人的明文 token（只显示这一次）──
9pIEW3TU5zwDheefEl7EzPgqCUlxxkQ2p_Xx9-ugbA4

── 追加到 .env 的 API_TOKENS 里 ──
sha256$c7a2c5e0f4b1493f656aa16c38cd92f37e1b199b787f5a92c2386ddaa30e4472:P01:director
```

把**上面那串**交给本人，**下面那行**追加到 `.env` 的 `API_TOKENS`（逗号分隔）。

> 明文只打印这一次，**不落任何文件**。落文件就等于又造了一份需要保护的东西。

### 2.2 把已有的明文配置转成散列

```bash
conda run -n schedule python -m backend.api.tokens_cli hash --tokens "$API_TOKENS"
```

明文条目**仍然能用**（兼容旧配置），但 app 启动时会打一条 WARN 点名是谁：

```json
{"event":"API_TOKENS 中仍有明文口令","users":["P01"],"level":"warning"}
```

### 2.3 轮换某个人的 Token

```bash
conda run -n schedule python -m backend.api.tokens_cli rotate --user P01 --tokens "$API_TOKENS"
```

打印新明文 + 替换后的整行。**新行生效的瞬间旧 token 失效。**

### 2.4 三条不肯让步的地方

1. **`API_TOKENS` 留空 = 全部拒绝**，不是全部放行。内网也不给这个后门。
2. **比对是常数时间的**（`secrets.compare_digest`），不用 `==`。
3. **角色不做默认**：`.env` 里写了一个认不出的角色，进程直接起不来 ——
   默认高了凭空发权限，默认低了挡住合法操作还没人知道为什么。

> 散列用的是**裸 sha256** 而不是 Argon2/bcrypt。理由：token 是
> `secrets.token_urlsafe(32)` 生成的 256 bit 随机串，没有字典可穷举，
> 慢哈希只换来每个请求几十毫秒的开销。**哪天改成用户自选口令，必须换成慢哈希。**

## 3. 审计

所有写操作与批准操作入 `audit_log`，四要素齐备：**操作人 · IP · 前后值 diff · trace_id**。

```sql
-- 最近的批准操作
SELECT ts, actor, actor_ip, action, resource_id, jsonb_pretty(diff)
FROM audit_log WHERE action = 'api.schedule.approve'
ORDER BY audit_id DESC LIMIT 20;

-- 某次运行的全部动作
SELECT ts, actor, actor_ip, action FROM audit_log
WHERE resource_id = '<trace_id>' ORDER BY audit_id;

-- 谁改过数据
SELECT ts, actor, actor_ip, resource_id, before->>'snapshot_id' AS from_snap,
       after->>'snapshot_id' AS to_snap
FROM audit_log WHERE action IN ('ingest.commit', 'api.ingest.confirm')
ORDER BY audit_id DESC;
```

一次批准的 `before` / `diff` 长这样：

```json
before: {"status":"AWAITING_HUMAN","plan_id":"2026W02-a77acefb65fc","sorties":14,
         "solver_status":"OPTIMAL","content_sha256":"a77acefb…","awaiting_human":true}
diff:   {"changed":{"status":{"before":"AWAITING_HUMAN","after":"DECIDED"},
                    "awaiting_human":{"before":true,"after":false}},
         "added":{"decision":"APPROVE","decided_by":"P01","comment":"确认归档"}}
```

**四条要知道的：**

1. **只追加，不更新不删除。** 同一资源被操作两次是两行。
2. **`actor` 记的是 `user_id` 不是 token。** 口令进日志是最经典的一类泄露。
3. **不采信 `X-Forwarded-For`。** 那个头客户端能随便写；采信它等于让审计可伪造。
   裸装部署里 uvicorn 直接面向内网，`request.client.host` 就是真实来源。
   将来真加了反向代理，要按「只信任已知代理转发的那一跳」改，而不是现在先埋默认信任。
4. **读操作不写审计。** GET 全部不留痕 —— 那只会把表撑到没人愿意翻。
5. **摄取确认有两行**：`ingest.commit`（数据怎么变的，与建快照同一事务）
   和 `api.ingest.confirm`（谁从哪台机器动的手）。两件事，两行。

## 4. 规则与语义

| 文件 | 管什么 | 改了会怎样 |
|---|---|---|
| `rules/ruleset_v1.3.yaml` | 14 条硬约束的参数（周转时间、休息间隔、密度上限…） | 版本串变 → 进 `content_sha256` → 历史计划按它生成时的版本判定 |
| `rules/semantics.yaml` | 13 条语义假设开关（S-01~S-13） | 同上。**切换任何一条都会改变排班结果** |

### 4.1 新增一条语义开关会被阻断

这是设计行为，不是 bug。`semantics.yaml` 里出现 `S-01~S-13` **之外**的开关时，
进程直接抛 `FTS-1002` 拒绝启动：

```
出现未裁定的语义开关 ['S-14'] —— 触发即意味着有人新增了未经业务方裁决的开关
```

**光在 yaml 里给它填个 `value` 也不放行**：允许的开关清单在**代码**里
（`backend/core/ruleset.py::REQUIRED_SWITCHES`），要加就得改代码 ——
那一步会进 code review、会留 git 记录、会被问「业务方哪天裁定的」。
**只改配置悄悄加一条语义假设这条路是走不通的**，这正是这道闸的用意。

### 4.2 知识层（`skills/`）可以随便改

`skills/` 下的 markdown 是给模型看的**解释材料**，业务方可以直接编辑。

> **改它不会改变任何一条排班结果。** 这一点有专门的测试证明：故意把
> 「约束7 的周转时间」在 skill 里写成 5 分钟，重跑基准周，输出方案的
> `content_sha256` **一个字节都不变**。

所以：**排班规则要改，改 `rules/` 下的 yaml；解释说得不好，改 `skills/`。**

## 5. 数据管理

```bash
# 摄取基准数据（四份 PDF → 基准快照）
conda run -n schedule python -m backend.ingestion.cli --baseline
conda run -n schedule python -m backend.ingestion.cli --baseline --dry-run   # 只看 Diff

# 上传路径（走人工确认门禁）
conda run -n schedule python -m backend.ingestion.cli <文件...> \
    --approver P01 --cycle-start 2026-01-05 --resolve "X1=2026-01-07"
```

**三条铁律：**

1. **抽取失败绝不静默降级**：脏 token 宁可抛 `FTS-1003` 阻断入库。
2. **源内冲突必须人裁**：同一份文件里前后矛盾的值（`FTS-2001`）会被**主动检出**
   并要求逐条裁定，系统不替你选。
3. **缺什么问什么**（`FTS-1004`）：少传一类数据 → 要求补传整份文件；
   缺课程周期起点 → 要一个日期。**没有默认值**，配置项里也不许加
   —— 那个值进主键，填错要迁移全表。

**快照是不可变的**：每次确认入库生成一个新的 `snapshot_id`（内容哈希），
旧快照保留。历史计划永远指向它生成时用的那个快照。

## 6. 安全

### 6.1 全离线

应用代码**没有任何出网路径**。三道闸：

| 闸 | 管什么 | 怎么验 |
|---|---|---|
| 代码层 allowlist | 所有 HTTP 客户端走 `core/http.py`，只放行 `127.0.0.1` 与内网段 | `pytest tests/guardrail/test_egress.py` |
| CI 静态扫描 | 全仓库不许直接 `import requests/httpx/urllib.request`；源码里不许有外部 URL 字面量 | `bash deploy/scripts/check_egress.sh` |
| 运行时抓包 | 跑一遍完整排班，抓 socket 层出站连接 | `pytest tests/guardrail/test_egress_e4.py` |

实测：一次完整排班的全部出站连接只有 **`127.0.0.1:5433`（PG）**
与 **`127.0.0.1:6380`（Redis）**。

compose 路径可额外加内核级封锁：`sudo bash deploy/compose/iptables_egress_drop.sh apply`。

### 6.2 文件上传

扩展名白名单（pdf/xlsx/docx/csv/png/jpg）+ **MIME 嗅探双验**（两者不一致直接拒收，
一个 `.csv` 后缀的 zip 过不去）+ 50 MB 上限 + 压缩炸弹检测（解压比 / 总体积 / 条目数
三条独立判据）+ **上传目录 0700、上传文件 0600，任何人不可执行**。

### 6.3 日志脱敏

`LOG_REDACT_PERSON=true`（默认开）时，日志里的人员姓名与 `P\d+` 编号替换为 `***`。

**只脱敏日志，不影响业务数据** —— 排班结果里的姓名必须原样保留，
否则 Excel 就没法拿去调度真人了。

> **导出文件不按角色分级**（业务方 2026-08-18 裁定）：所有能调 `/export` 的角色
> 拿到完全相同的 xlsx。查看者已经被 RBAC 限制在只读，而排班员往下都要拿着表
> 去调度真人，姓名是必需的。

### 6.4 模型完整性

Ollama 模型固定 digest，**体检时与应用启动时双重校验**（同一份判据，
`backend/core/integrity.py`）。不匹配时**进程直接起不来**：

```bash
conda run -n schedule python -m backend.core.integrity --require
```

发现不匹配时：核对模型来源，**不要绕过校验**。临时可把 `LLM_PROVIDER=mock`
让系统先跑起来（排班能力不受影响），但必须查清模型为什么变了。

### 6.5 机密管理

`.env` 已在 `.gitignore` 里；模型权重与 `data/` 下大文件不入 Git。
备份 `.env` 时按机密件处理（里面有 token 散列与数据库口令）。

## 7. 错误码速查（16 个）

| 码 | 含义 | 用户该做什么 |
|---|---|---|
| FTS-1001 | 规则文件解析失败 | 修 yaml；旧规则版本继续服务 |
| FTS-1002 | **有未裁定的语义开关** | 走裁定流程；见 §4.1 |
| FTS-1003 | PDF 抽取后置断言失败 | 按提示的残缺 token 与页码修数据后重传 |
| FTS-1004 | 必需输入缺失 | `answer` 类给个值，`upload` 类补传整份文件 |
| FTS-2001 | 数据引用完整性失败**或源内值冲突** | 按裁定表逐条裁决 |
| FTS-3001 | 约束不可满足 INFEASIBLE | 看最小冲突集与松弛提案 |
| FTS-3002 | 求解超时 UNKNOWN | **不等于无解**；延长时限 |
| FTS-3003 | **求解器与校验器判定分歧** | **CRITICAL**，不出结果，立刻报开发 |
| FTS-3004 | 恢复时快照已变更且影响本方案 | 基于新快照重解 |
| FTS-3005 | 多轮修订致不可行 | 已回滚到上一版；换个说法 |
| FTS-4001 | LLM 不可用 | **排班不受影响**，改用表单入口 |
| FTS-4002 | LLM 输出不符 schema | 自动重试 2 次；仍失败转人工表单 |
| FTS-4003 | 超出 Harness 预算 | 缩小请求范围 |
| FTS-4004 | LLM 组件越权调用工具 | **直接拒绝不重试**；`architectural_ban` 档视为架构缺陷 |
| FTS-4005 | **状态冲突**：有人在排同一周，或该运行现在不能决策 | 等对方跑完或等运行走到门禁；**不排队** |
| FTS-5001 | Excel 写出或回读校验失败 | 不交付文件，中间 JSON 保留 |

> **FTS-4005 与 FTS-3004 不要混。** 前者是「数据没变、只是现在不能做」（等一等），
> 后者是「数据变了要重解」（重跑）。用户的下一步完全不同。

## 8. 并发

**两把锁：**

1. **`(tenant, week)` 排班锁**（API 提交期取）：两个人排同一周时后者立即被拒
   （`FTS-4005` / HTTP 409），**不排队**。响应里带 `holder` 与 `ttl_s`，
   前端据此提示「谁在排、还剩多久」。走到人工门禁时**主动放锁**
   （之后可能停一整天等人确认）。
2. **`snapshot_id` 锁**（worker 执行期取）：堵住「不同周、同快照」在
   `training_progress` 上的死锁。代价是同一快照的排班全局串行 ——
   排一周班是分钟级的重操作，不是并发热点。

**没有速率限制。** v6 §11.5 未要求，M8 也没有自造：`/chat` 与 `/schedule`
的保护只有上面两把锁（锁只拦同一周）。一个人狂点会把 RQ 队列塞满 ——
内网可信环境下这是可接受的，**要加限流需先走规格裁定**。

## 9. 定期检查清单

| 频率 | 做什么 |
|---|---|
| 每日 | `bash deploy/native/healthcheck.sh`；看 `audit_log` 当日的 approve 记录 |
| 每周 | 数据库备份；确认 `data/plans/` 归档完整 |
| 每月 | 检查 `API_TOKENS` 里有没有离岗人员；清理 `data/uploads/` 超期目录 |
| 每季 | Token 轮换；核对模型 digest；跑一遍 `golden_fingerprint` 与出厂值比对 |
| 规则变更后 | 跑 `pytest tests/golden tests/guardrail`；重新导出 OpenAPI |
